# ADR-0001: 规范层与执行层的物理分离

- **状态**：accepted
- **日期**：2026-11-11
- **决策者**：人类责任方（项目发起）
- **serves_charter**：C3（自包含）、C6（知识可检索、规则可检查）
- **grounding_refs**：无（本决策是治理结构决策，不锚定外部来源）
- **affected_files**：`CHARTER.md`（新建）、`CONSTITUTION.md`（新建）、`GRAMMAR.md`（新建）、`SOURCE_LEDGER.md`（新建）、`spec/`（新建）、`AGENTS.md` 第 4 条

## 背景

软件工程技能的教训：成文法与成文法本身的治理混在同一批文件中，导致规则演进时无法区分"规则内容变了"与"治理程序变了"；ADR 目录退化为第二套规则文本；来源登记表与规则文本互相污染。

本技能不能重复这个错误。需要一个结构，使得：
- 规则的内容（什么算合法的项目管理断言）与规则的治理（谁可以修改规则、如何修改）不在同一个文件里；
- 来源的登记（外部锚点）与规则的使用（内部条件式）不在同一个文件里；
- 执行规范（如何编译为检查程序）与立法文件（规则本身）不在同一个文件里。

## 决定

技能的物理结构分为四层，每层有独立的文件与独立的变更权限：

1. **意图层**（`CHARTER.md`）：技能为什么存在、承诺什么。修改需 ADR 且须论证具体技能失败。
2. **治理层**（`CONSTITUTION.md` + `adr/`）：成文法由谁修改、如何修改、什么算合法修改。修改需更严格 ADR。
3. **立法层**（`GRAMMAR.md` + `SOURCE_LEDGER.md`）：规则内容与来源锚定。修改需 ADR + 来源支撑。
4. **执行层**（`spec/` + `contracts/` + `validation/`）：把立法翻译为可运行的检查与准入条件。结构性变更需 ADR；非结构性变更不需。

四层之间的关系是：**执行层不得修改立法层；立法层不得修改治理层；治理层不得修改意图层**。反向的修改只能通过 ADR 通道。

## 考虑过的替代方案

**替代方案 A：单文件结构**（所有内容在一个 `SKILL.md` 中）。拒绝理由：这正是软件工程技能的教训；无法分离规则演进与治理演进。

**替代方案 B：两层结构**（立法 + 执行，治理内嵌在立法中）。拒绝理由：治理规则会与规则内容混排，"这条规则为什么可以这样改"与"这条规则说了什么"无法区分。

## 结果

### 正面

- 规则内容、治理程序、来源登记、执行规范各有唯一权威位置，不互相污染。
- ADR 只记录治理决策，不退化为第二套规则文本。
- 来源的版本状态与规则的锚定关系可独立维护（`SOURCE_LEDGER.md` 的状态变更不要求修改 `GRAMMAR.md` 的规则陈述）。
- 执行层的结构性变更可被识别并走 ADR，非结构性变更可快速迭代。

### 负面

- 文件数量增加；读者需要理解四层结构才能定位内容。缓解：`README.md` 提供三条阅读路径（首次接触 / 日常使用 / 治理修改）。
- 规则与来源的跨文件引用需要维护一致性。缓解：`SOURCE_LEDGER.md` 的 `claim_mapping` 字段提供论断级映射；`GRAMMAR.md` 的 `grounding_ref` 与 `claim_mapping` 双向校验登记于 `TODO.md`。
