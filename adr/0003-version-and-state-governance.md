# ADR-0003: 版本与状态治理——包层单一版本、文件层不承载

- **状态**：accepted
- **日期**：2026-11-11
- **决策者**：用户（人类责任方）批准，执行方落地
- **serves_charter**：不修改 C1–C6；本决策服务于 C5（版本发布与状态裁定由人类责任方保留，不由执行方自行声明）
- **grounding_refs**：无（技能自身的治理决策，不对应 `SOURCE_LEDGER.md` 的条目）
- **affected_files**：
  - 本 ADR 落地时：`STATE.md`（登记本文件）、`CHANGELOG.md`（批次 0006）、`TODO.md`（T-109、T-110）
  - 后续批次：`CONSTITUTION.md` 第 9 条与第 11.7 条、`AGENTS.md` 第 4 条、`README.md`、`ERRATA.md`、`TODO.md`（关闭 T-108）、`STATE.md`、`scripts/`、`manifest.json`
  - 待裁定：`spec/COMPILATION_META.md` 第 10 条、`spec/methods/deterministic-checker.md` 第 9 节（产物版本链，见“需要跟进的事项”）

## 背景

本技能最初以对话交付物的形态产生，每个文件自带版本头（`v0.1`/`v0.2`/`v0.3`）、文件级状态行，以及 `README.md` 的“状态与版本”段。**在没有版本控制时，文件头是唯一可追溯的版本与状态载体**，这一做法在当时是必要的。

仓库已 `git init` 并完成若干批次提交后，继续保留文件头版本产生了三个具体失败：

1. **版本无法回答“这个包是哪个版本”**。每个文件各自递增版本号，同一包内版本号互不相同（`GLOSSARY.md` 一个、`spec/` 一个、方法声明又一个），外部技能引用本包时没有任何单一标识可指向。
2. **状态双写且无对账**。文件头状态与 `STATE.md` 可同时存在且互相矛盾；`STATE.md` 是人工维护的，没有机械检查能发现“文件漏登”“登了已删除的文件”“状态值非法”。
3. **版本口径已发生冲突**。落地分享内容时，交付正文自带 `**版本**：v0.1`、`v0.4` 等表述，与仓库既定的去版本口径冲突，只能逐条不落地并登记 `ERRATA.md` E-008、E-010；冲突是症状，根因是“版本与状态的载体”没有治理决策。

`TODO.md` T-108 已登记该冲突：`CONSTITUTION.md` 第 9 条与第 11.7 条仍要求“版本号在文件头声明”。

## 决定

**文件层不承载版本，也不承载状态；包层只保留一个版本，以 annotated git tag 声明；状态由 `STATE.md` 唯一承载。**

具体规则：

1. **文件层**：任何文件不写版本号、不写文件级状态。文件的历史由 git 承担；某文件的当前状态查 `STATE.md`。
2. **包层**：包版本只有一个，以 annotated tag 标记发布点，tag 说明即发布说明。不设“文件版本”与“包版本”的映射关系。
3. **外部引用**：包被外部技能引用时，根目录 `manifest.json` 记录包版本与契约 schema 版本；`pm_contract_version` 一类**接口版本是数据字段**，保留不动，不受本决策约束。
4. **状态**：`STATE.md` 仍是唯一状态来源。状态按目录给默认值（`spec/` 为 `active`、`adr/` 为 `accepted`、模板类为 `template` 等），只对例外显式标注。新增 `scripts/check_state.py`，用 `git ls-files` 对账：文件漏登、登了不存在的文件、状态值非法均报错。
5. **版本号规则**：按治理含义递增——
   - **major**：规范条文或契约 schema 不兼容；
   - **minor**：新增规范或文件；
   - **patch**：纯澄清与 errata。
6. **首个包版本 `v0.4.0`**：此前文档最后声称的版本是 `v0.4`，取 `v0.4.0` 可避免版本号倒退；`v0.4.0` 是 `v0.4` 在 semver 下的规范化写法，不表示新增了 `v0.4` 之外的内容。

## 考虑过的替代方案

1. **保留文件头版本，同时使用 git**。拒绝：版本双写必然漂移，且没有自动一致性检查；同一包内多版本号无法被外部引用。
2. **用 CHANGELOG 批次号当作包版本**。拒绝：批次是“一次变更”的粒度，不等于“一个发布点”；外部引用需要稳定、可比较的标识，批次号只增不减且与兼容性无关。
3. **用 git commit hash 当作包版本**。拒绝：hash 不可读、不可比较，无法表达“major/minor/patch”的治理含义；tag 已经承载了“指向某次提交”的能力。
4. **首个包版本取 `v1.0.0`**。拒绝：`v1.0.0` 夸大了成熟度（本包尚未接地，`spec/GROUNDING_CRITERIA.md` 的六判据未全部满足）；且与文档最后声称的 `v0.4` 不一致，构成版本号跳跃。
5. **文件层保留“仅状态、不保留版本”**。拒绝：状态同样有唯一来源（`STATE.md`），双写问题与版本同构；状态又天然可按目录给默认值，更适合集中登记。

## 结果

### 正面

- 包版本单一、可引用：外部技能只需读 tag 或 `manifest.json`，不必推断“哪个文件的版本号算数”。
- 文件状态单一来源，且可机械对账：`scripts/check_state.py` 以 `git ls-files` 为准，消除三类人工漏登。
- 版本递增具备治理含义：major/minor/patch 对应“兼容性 / 新增 / 澄清”，与 `CONSTITUTION.md` 第 4 条的结构性变更判定可以对齐。
- 与既有 `ERRATA.md` E-008、E-010 的取舍获得治理依据，不再是执行方的临时口径。

### 负面

- 脱离 git 的单文件副本不再自带版本与状态。可接受：本技能的交付单位是仓库，不是散落文件。
- 发布流程依赖“记得打 tag”。遗漏 tag 会使包没有可引用版本，需要靠流程纪律而非文件内容保证。
- `manifest.json` 的包版本与最新 tag 存在第二处记录，需要一致性检查（登记 T-110）。
- 产物版本链（`spec/methods/deterministic-checker.md` 第 9 节以文件版本为输入）失去输入，必须重构；重构方式涉及编译语义，需另行裁定（登记 T-109）。

### 需要跟进的事项

- **T-108**（关闭）：`CONSTITUTION.md` 第 9 条、第 11.7 条的修订。
- **T-109**（新增，已由 ADR-0004 裁定）：`spec/COMPILATION_META.md` 第 10 条与 `spec/methods/deterministic-checker.md` 第 9 节以“文件头版本”为输入定义产物版本与对齐检查；文件层去版本后该链失效。替代口径见 **ADR-0004**：产物记录生成基线的 `source_commit`，装配时比对源提交，脏工作区直接判定过期。
- **T-110**（新增）：`manifest.json` 的包版本与最新 annotated tag 的一致性检查。
