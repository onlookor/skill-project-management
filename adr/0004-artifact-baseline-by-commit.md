# ADR-0004: 编译产物基线由 git 提交标识

- **状态**：accepted
- **日期**：2026-11-11
- **决策者**：用户（人类责任方）批准，执行方落地
- **serves_charter**：服务于 C6（知识能以确定性查询被检索）的运行时纪律——Agent 不得运行过期编译产物
- **grounding_refs**：无（技能自身的治理决策，不对应 `SOURCE_LEDGER.md` 的条目）
- **affected_files**：`spec/COMPILATION_META.md` 第 3.6 节、第 7.5 节（及第 7 条编译产物段）、`spec/methods/deterministic-checker.md` 第 9 节、`CONSTITUTION.md` 第 9 条（间接）、`adr/0003-version-and-state-governance.md`（交叉引用）
- **相关**：ADR-0003（文件层去版本是本案的前提）

## 背景

ADR-0003 决定文件层不承载版本号。在该决定之前，编译域的“防过期产物”机制建立在文件版本之上：

- `spec/COMPILATION_META.md` 第 7.5 条：“编译产物的版本必须与 `GRAMMAR.md` 版本、`SOURCE_LEDGER.md` 版本、方法版本三者对齐。任一变化触发重编译。”
- `spec/methods/deterministic-checker.md` 第 9 节：“产物版本 = f(`GRAMMAR.md` 版本, `SOURCE_LEDGER.md` 版本, 方法版本)”，宿主装配时校验产物版本与源版本一致，不一致拒绝运行过期产物。
- `spec/COMPILATION_META.md` 第 3.6 节要求方法声明“产物版本与源版本的对齐方式”。

文件层去版本后，这一链条**没有输入**：没有文件版本可供比较，“产物版本 = 源版本函数”无法求值。若不处理，要么保留名存实亡的版本字段（违反 ADR-0003），要么静默放弃过期检测（违反第 7.5 条与承诺 C6 的运行时纪律）。

此外，版本号比较本身有一个既有缺陷：**它无法区分“源文件已改但未递增版本号”**。版本号是人工维护的，只要有人改内容忘递增，比对就会给出假通过。git 提交恰好补上这一点：内容是否变化由提交与工作区状态直接回答。

## 决定

**编译产物的基线由生成该产物时的 git 提交标识；装配时比对当前源提交，不一致即拒绝运行；源文件相对基线有未提交改动时，直接判定过期。**

具体规则：

1. **产物携带 `source_commit`**：每个编译产物（`validation/CHECKLIST.md` 与各方法的检查项规格）记录生成时的 `source_commit`——即 `GRAMMAR.md`、`SOURCE_LEDGER.md`、方法声明、`knowledge/` 谓词定义这些源文件所在的 git 提交。
2. **对齐检查**：宿主装配时比对产物的 `source_commit` 与当前源提交。不一致 → 拒绝运行过期产物（原第 7.5 条的拒绝语义保留）。
3. **脏工作区**：若任一源文件相对 `source_commit` 存在未提交改动，产物直接判定过期，**不得**以“提交号相同”放行。
4. **无 git 环境**：无法取得提交标识时，不得假定产物有效；按“无法证明对齐”处理，拒绝运行并报告部署缺陷。
5. **重编译触发**：`GRAMMAR.md` 规则增删改、`SOURCE_LEDGER.md` 条目状态变更、方法声明变更、`knowledge/` 谓词定义变更，均触发重编译；重编译后产物记录新的 `source_commit`。

## 考虑过的替代方案

1. **取消产物级版本与对齐检查**，只保留“重编译触发条件”，过期检测交给部署方。拒绝：直接放弃第 7.5 条的保护，Agent 可以在规则已变的情况下继续运行旧检查清单，且没有任何机械信号提示；这会让“编译产物”退化为一次性快照。
2. **保留文件版本，仅用于编译对齐**（版本号只服务编译域，不对外）。拒绝：这正是 ADR-0003 否决的“双写”；且仍然无法发现“改了内容没递增版本”。
3. **用产物内容哈希作为标识**，比对源文件哈希。拒绝：哈希能回答“变没变”，但不能回答“产物是否落后于源”，且每次装配都需重算全部源文件哈希；`source_commit` 语义更直接，也与发布（tag）共用同一套 git 标识。
4. **记录生成时间戳 + 人工确认**。拒绝：时间戳不能证明源一致；人工确认无法机械化，违反 `AGENTS.md` 第 2 条“可确定性执行的动作一律外化”。

## 结果

### 正面

- 过期检测有确定输入：`source_commit` 与当前提交可直接比较，不依赖人工递增版本号。
- 脏工作区被显式覆盖：修复了原版本号机制“提交号相同但内容已变”的假通过路径。
- 与发布机制同源：包版本用 tag、产物基线用提交，均以 git 为唯一事实来源。
- 拒绝语义保留：过期产物仍然被拒绝运行，不是“只记录不校验”。

### 负面

- 产物必须写入 `source_commit`，产物生成流程增加一步（`validation/CHECKLIST.md` 需在生成时记录）。
- 依赖 git 可用性：导出为脱离仓库的副本后无法做对齐检查，只能拒绝运行。
- 每条产物只对应一个基线提交；多方法共存时，各产物需各自记录基线，不能共享一个“包级基线”字段。

### 需要跟进的事项

- **T-110**（保持 `open`）：`manifest.json` 的包版本与最新 annotated tag 的一致性检查，与本案的 `source_commit` 检查互补。
- **T-111**（新增）：为 `validation/CHECKLIST.md` 补充 `source_commit` 字段并在生成流程中写入；在此之前，现有清单视为“基线未记录”，装配时按过期处理。
