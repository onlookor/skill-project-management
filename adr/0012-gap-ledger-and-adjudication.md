# ADR-0012: 以缺口台账与到期裁定治理“规则严于判定列”

- **状态**：accepted
- **日期**：2026-11-14
- **决策者**：用户（人类责任方）批准建立临时机制；执行方落地台账、检查器与条文
- **serves_charter**：不修改任何承诺；服务于 C6（可机械检查、可审计）与 C3（来源封闭、可追溯）的维护条件
- **grounding_refs**：无（本决策针对治理结构自身，不依赖来源条目）
- **affected_files**：`GAP_LEDGER.md`（新建）、`scripts/check_gap_ledger.py`（新建）、`AGENTS.md`（新增 3.6、第 4 条目录树、7bis 第 4–5 条）、`ROADMAP.md`（M1 / M3 工作项与出口、D4、发布门槛）、`TODO.md`（T-132；T-100 / T-130 / T-131 交叉引用）、`scripts/README.md`、`.githooks/pre-commit`、`scripts/check_state.py`、`CHANGELOG.md`

## 背景

T-011 在补齐 17 个 `check_id` 的输入/输出样例时，暴露了一类结构性问题：**规则正文的规范性条件严于判定列**。具体有四条：

1. G-A2 的“管理活动/产物”节点类型未在输入 schema 中枚举（G-001）。
2. G-D2 的“验证条件满足前不得作为批准依据”没有批准关系的载体（G-001）。
3. G-E1 的“决策类 `Commitment`”筛选谓词未定义（G-001）。
4. G-A1 的约束作用边、G-E2 的 `assumption` 形式条件未进入判定列（G-002、G-003）；`ROLE_MINIMAL_COMPLETENESS` 把两种严重度压在同一级别（G-004）。

这些发现此前只以 T-130、T-131、T-100 三条独立 TODO 存在，另有三个未定义判定对象没有落脚点。问题在于：

- **没有统一入口**：同类问题在不同提交里以不同形式出现，是否登记依赖执行者自觉。
- **没有到期**：TODO 可以无限 `open`，不会阻断任何动作。
- **没有出口**：裁定结果可以是“再看看”，没有强制落到改规则、改判定、降为文档约束或接受现状。
- **没有机械核查**：无法回答“现在有几条缺口、几级、几条到期”。

用户明确要求：缺口今后可能扩大，需要一套最小可执行、可机械核查的临时治理机制。

## 决定

建立**缺口台账 + 到期裁定 + 四出口 + 机械核查**的临时机制：

1. **台账**：`GAP_LEDGER.md` 是缺口的唯一登记处。编号 `G-NNN` 连续分配。G-D2、G-A2、G-E1 归并为一条 `G-001`（成因 `undefined-object`：“规则引用了注册表中未定义的判定对象”）；T-130、T-131、T-100 保留独立编号，分别交叉引用 `G-002`、`G-003`、`G-004`，并在台账中说明四者同属“规则正文严于判定列”这一大类。
2. **入口**：`undefined-object` / `rule-stricter` / `severity-mismatch` 三类成因各给机械判据（词表差集、规范性子句切分、A 表与 `CHECKLIST.md` 比对）。台账的核查矩阵必须逐行覆盖附录 A 全部 `check_id`，结论只能是 `consistent` 或缺口编号。
3. **分级**：L1 阻断错判（停留 1 个里程碑）、L2 漏判（2）、L3 语义不可判定（2）。到期 = 登记里程碑 + 停留上限；到期未裁定即阻断。
4. **裁定点**：台账头部维护 `**当前里程碑**：M#`；跨过到期里程碑前必须裁定或显式降级（只允许一次，须写“降级理由：”）。
5. **四出口**：`rule-change` / `check-change` / `doc-only`（注明“不检查”）/ `accepted`（注明“理由：”）。`open` 条目不得预填出口。
6. **机械核查**：`scripts/check_gap_ledger.py` 统计总数、按级与按到期计数，校验字段枚举、矩阵覆盖、TODO 交叉引用；到期未裁定退出 1。`--staged` 要求规则/判定文件与台账同批暂存。检查器接入 `.githooks/pre-commit`，并由 `check_state.py` 调用，使到期未裁定阻断发布。
7. **临时性**：连续两个发布点 `open=0` 且矩阵 17/17 `consistent`、第二个周期无新增、全量对照无 `rule-stricter` 遗留时可撤除；硬约束为不晚于 M3 关闭前评估（`TODO.md` T-132）；M3 关闭时仍有 `open` 则冻结，新增缺口须经 ADR，所有 `open` 须在 M4 前裁定。

## 考虑过的替代方案

1. **只扩充 TODO，不建台账**：拒绝理由。TODO 的粒度是“单点工作项”，无法表达“同一口径缺陷的多条表现”；也没有到期与阻断语义，会继续无限挂账。
2. **写进 `CONSTITUTION.md`**：拒绝理由。这是**临时操作机制**，不是永久治理结构。写进宪法会把它固化，撤除时又要走宪法修订程序；机制的目标恰恰是让自己在缺口清零后消失。因此只写入 `AGENTS.md`，并在台账与 ADR 中声明临时性。
3. **把缺口检查并入 `check_state.py`**：拒绝理由。`check_state.py` 已承担 STATE 对账与发布一致性，再加入台账解析会让两个不相关的失败域混在一个退出码里；独立脚本便于 `--staged` 单独调用，也便于撤除时整文件删除。
4. **在检查器里做完整语义判定**：拒绝理由。`rule-stricter` 需要判断“子句是否在判定列有对应项”，当前无法可靠机械化；机制只把**覆盖与到期**机械化，把语义判断留给人工复核，但通过“矩阵全覆盖 + 同批更新”保证人工复核不可静默跳过。

## 结果

### 正面

- 四类问题有统一入口与编号；G-001 的归并消除了“三个未定义判定对象没有落脚点”的状态。
- 到期与发布阻断把“以后再说”变成可机械发现的失败。
- 四出口消除了沉默裁定。
- 机制自身有撤除条件与里程碑归属，不会变成永久负担。

### 负面

- `rule-stricter` 的识别仍依赖人工判断；检查器只能保证“每个 `check_id` 都被表态”，不能保证表态正确。
- 新增第五个提交前检查器，提交路径变长。
- 台账与 `TODO.md` 存在有意保留的交叉引用（G-NNN ↔ T-NNN），需要两边同步更新；这是“保留独立编号”的代价。

### 需要跟进的事项

- T-132（M3）：评估并撤除本机制。
- T-100（G-004，L1）：在推进到 M2 前裁定或显式降级，否则 `check_gap_ledger.py` 退出 1。
- T-130（G-002）、T-131（G-003）：在 M3 前裁定。
- G-001（L3）：在 M3 前给出 `doc-only` 或输入 schema 定义的裁定。
