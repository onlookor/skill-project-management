# ADR-0014: 验证链自证问题与验证权绑定

- **状态**：`proposed`（2026-11-14）
- **日期**：2026-11-14
- **决策者**：架构负责人（按用户批准执行）；人类责任方已批准方向
- **serves_charter**：C3（来源封闭、可追溯）、C6（可机械检查、可审计）的维护条件
- **grounding_refs**：无（决策针对验证机制本身，不依赖来源条目）
- **affected_files**：`scripts/check_checker_pins.py`、`scripts/check_spec_pins.py`、`scripts/checker-pins.json`、`scripts/spec-pins.json`、`validation/pinned/checker.py`、`scripts/check_coverage_gate.py`、`validation/checker-prototype/coverage.json`、`.githooks/pre-commit`、`AGENTS.md`、`ROADMAP.md`、`CHANGELOG.md`

## 1. 问题：验证链不能自证

绿色数字来自一条闭环：规格 → 样例 → 检查器 → 结论。闭环里的每一环都放在同一个工作区，由同一方修改：

- 改规格（`GRAMMAR.md`、A.2、schema），再让样例与检查器跟随；
- 改检查器或样例期望，让失败变通过；
- 改登记值/快照，让“绑定”本身自洽。

如果只报告“57/57 通过”，机器无法区分“规则被遵守”与“判定标准被改到刚好通过”。这不是某个检查器的缺陷，而是验证权与被执行权没有分离。

**信任边界**：本仓库信任的是“提交内容与提交评审”，不是“工作区里的绿色数字”。机器只能把改动变成显式、可追溯的事件；它不能证明改动人诚实，也不能证明复核者独立。

## 2. 信任边界与各层能力

| 层 | 谁能改 | 机器能验证 | 机器不能验证 |
|---|---|---|---|
| 规格（`GRAMMAR.md`、A.2、schema §2bis/§3/§4） | 仓库写权限持有者 | 区段指纹是否变化、是否附复核记录字段 | 改动是否语义正确、复核者是否非同源 |
| 样例与覆盖矩阵 | 仓库写权限持有者 | 每子句是否有 1 正 1 负、样例方向与原因码是否匹配 | 样例是否真正覆盖子句语义、是否足以证伪 |
| 检查器脚本 | 仓库写权限持有者 | 哈希是否等于登记值、改动是否带 `basis` | 改动是否合理、是否被同一方与样例同改 |
| 验收检查器快照 | 仓库写权限持有者 | 与工作区副本是否字节一致（漂移检测） | 两份文件是否被同一方同改 |
| 复核记录 | 仓库写权限持有者 | 是否含规定字段与结论词 | 记录是否真实、签收人身份与独立性 |
| 提交本身 | 提交者 | 钩子是否运行、文件是否同批 | 作者身份、是否使用 `--no-verify` |

## 3. 决定：四道绑定

### 3.1 检查器绑定（可机械化）

`scripts/checker-pins.json` 登记 `scripts/` 下全部检查器脚本的 sha256 与 `basis`。`scripts/check_checker_pins.py` 在 pre-commit 比对工作区哈希与登记值，不一致即退出 1。改动检查器必须运行 `--write --basis "<裁定依据>"`；无 `basis` 的 `--write` 被拒绝（退出 2）。

目标不是阻止改检查器，而是让“改检查器”从静默变成显式，并在登记项里留下裁定依据。正负例：`scripts/test_checker_pins.py` CP01–CP04。

### 3.2 规格区段绑定（部分机械化）

`scripts/spec-pins.json` 分别登记以下区段的指纹：

- `GRAMMAR.md` 全文；
- 方法文件 A.2 区段；
- `spec/CHECKER_INPUT_SCHEMA.md` 的 §2bis、§3、§4。

`scripts/check_spec_pins.py` 比对当前指纹与登记值，并比较区段相对 `HEAD` 是否变化。任一区段变化时，同一提交必须附 `validation/reviews/*.md` 复核记录，且记录须同时含 `非同源复核：`、`区段：<key>`、`复核产物：<文件名>` 与结论词（实质收敛/认可/通过），否则退出 1。

这条把“改规格 + 同步签收”从一次静默操作变成三件必须同批出现的事：规格改动、指纹更新、复核记录。正负例：`scripts/test_spec_pins.py` SP01–SP04。

### 3.3 验收检查器与工作区副本（做不到真正分离）

仓库保留 `validation/pinned/checker.py` 作为验收检查器的只读快照，`check_checker_pins.py` 校验它与 `validation/checker-prototype/checker.py` 字节一致。

**明确限制：这不是权限分离，也不冒充分离。** 两份文件都在同一工作区、同一写权限下，同一方可以同时修改两份并重跑 `--write`，漂移检测会保持“一致”。真正的分离需要：验收运行使用提交者写不到的位置（CI 的受保护分支检出、签名发布物、只读挂载），并且复核者能独立读取该位置。当前仓库在本机运行、无 CI、无受保护分支，因此**做不到**真正的版本分离；本层只提供漂移检测与变更留痕。

### 3.4 非同源复核（不可机械化）

“复核者未参与实现”“复核记录真实执行”“结论词是否被授权使用”都无法由机器验证。它们只能靠：

- 3.6.6 的缺口关闭证据格式；
- 3.6.7 的 A.2 签收纪律；
- 3.6.8 的区段/检查器绑定；
- 以及提交评审与人类责任方的最终判断。

机器能做的是要求记录存在、字段齐全、与改动同批；不能做的是证明记录为真。

## 4. 机械化清单

| 动作 | 机制 | 类型 |
|---|---|---|
| 改检查器不留痕 | 哈希登记 + `basis` | 机械阻断 |
| 改规格不同步签收 | 区段指纹 + 复核记录字段 | 机械阻断（记录真实性除外） |
| 验收副本漂移 | 快照哈希比对 | 机械检测 |
| 删负例 / 负例改成正例 | 覆盖矩阵 + 方向/原因码核对 | 机械阻断 |
| 复核者是否独立 | 无 | 只能靠流程 |
| 复核记录是否真实 | 无 | 只能靠流程 |
| 检查器与登记/快照同改 | 无 | 残余风险（见第 5 节） |

## 5. 残余风险

1. **签收人身份不可验证**：机器只能读记录里的字符串，无法确认签收人是谁、是否参与实现。
2. **检查器、登记与快照可被同一方同改**：`--write` 会同时更新哈希与快照；有写权限的一方可以让三者自洽。
3. **复核记录可伪造**：字段齐全不等于复核发生。
4. **钩子可绕过**：`--no-verify` 或未启用 `core.hooksPath` 时，全部绑定不运行；只能靠提交评审发现。
5. **本地仓库无 CI**：没有独立执行环境，无法提供“提交者不可改”的验收副本。
6. **覆盖 ≠ 充分**：1 正 1 负只证明每个子句被至少一个方向触碰，不证明样例能证伪子句的全部语义变体。
7. **指纹绑定文本，不绑定意图**：区段指纹证明内容一致，不证明修订动机合法。

## 6. 后果与 M2 出口

正向：静默修改检查器/规格/样例的路径被收窄为“显式修改 + 留痕”；每一条绑定都有固定正负例；限制被写清，不再用哈希校验冒充权限分离。

负向：每次规格修订都要附复核记录，提交成本上升；绑定本身增加维护面；无 CI 环境下仍不能对抗有写权限的恶意同改。

**M2 出口**改为：G-009 与 G-014 关闭 + 覆盖闸门绿（41/41 子句各 1 正 1 负）+ 四道绑定生效（检查器哈希、规格区段指纹与复核记录、验收快照漂移检测、非同源复核判“实质收敛”）+ 其余 15 条缺口状态不变。
