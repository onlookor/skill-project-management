# ADR-0020: 案例素材不入来源登记表，以 MANIFEST 管理、只有评分判据入表

- **状态**：accepted
- **日期**：2026-11-15
- **决策者**：用户（人类责任方），批次 0081 批准
- **serves_charter**：C6（知识可检索、规则可检查）；不修改任何承诺
- **grounding_refs**：无（治理自身的决策）
- **affected_files**：`SOURCE_LEDGER.md`（新增“案例素材”处置说明与五条 EVM 来源的使用条件）、`TODO.md`（T-156）、`validation/cases/`（新建目录与 MANIFEST，待 T-156 落地）

## 背景

D6 验收需要任务集（公开案例改造，真实 ≥20 题、合成 ≤10 题），素材是**数据**，不是标准，也不是本体。按 `CONSTITUTION.md` 第 2.1 条，入表须满足三条件之一（公开发布的标准或规范 / 同行评议或可检索的学术本体 / 技能已接受的上游本体）——案例素材三条都不满足；按第 2.6 条，落点只能是 `rule:` / `knowledge:` / `method:` / `check:`，否则只能写 `pending:`。素材不支撑任何规则与术语，拿不到合法落点。

同时，第 2.3 条要求“本地副本应入表”。若按字面套用，每一个案例文件都要进登记表，结果是表里堆满永远无法闭合的 `pending:` 条目——这与 G-017 那类“挂了但永远不落地”的问题同构，且会让“入表”这一动作失去区分度。

## 决定

**案例素材不入 `SOURCE_LEDGER.md`。** 素材放 `validation/cases/`，每个素材集附 `MANIFEST`，记载：来源、许可、日期、改造说明、与任务集的对应关系。**只有由案例抽象出的评分判据**（如“该工件必须含 WBS 成本映射”）才入表，且必须落在 `rule:` 或 `check:` 上。

本条同时明确：`CONSTITUTION.md` 第 2.3 条的“本地副本应入表”**不适用于数据素材**。第 2.3 条约束的是**被引用为论断依据的文献副本**——入表是为了让 `grounding_ref` 可追溯到版本与核验状态；素材不承担论断，只提供任务输入与真实数字，因此不在其射程内。**宪法正文不修改**，本条只作解释性适用，不新增也不削减任何禁令。

## 考虑过的替代方案

1. **另立一类“案例素材”入表（新增 `authority_tier` 或 `status` 值）。** 否决理由：登记表的封闭枚举服务于 `grounding_ref` 的可解析性，扩表会让“每个表项都必须能支撑某条规则或术语”这一硬性区分失效；且一旦素材可入表，`pending:` 条目会随素材数量线性增长，维护成本与噪声都不可接受。
2. **按第 2.3 条逐份入表，接受 `pending:` 挂账。** 否决理由：即第 2.6 条明文禁止的形态——表项永远无法闭合，等于把“待核验”固化成常态；G-017 已经证明这类挂账会遮蔽真实缺口。
3. **素材不入库，只在任务集里写外部路径。** 否决理由：任务集必须可复现，外部路径会漂移，且许可状态无法随仓库审计；仓库内 `validation/cases/` + MANIFEST 保留了可审计性与可复现性，代价只是仓库体积。

## 结果

### 正面

- 登记表保持“每项都有落点”的强约束，`D3`（来源可追溯）不被素材噪声稀释。
- 素材的许可、来源、改造过程有统一登记位置，可审计、可复现。
- 评分判据仍走正常入表路径，判定依据与素材本身分离——**素材变了不影响判据的来源归属**，反之亦然。

### 负面

- 新增一套 `validation/cases/MANIFEST` 的维护口径，与登记表并存，存在两处不同步的风险。
- 仓库体积随素材增长；许可不允许入库时只能留指向外部持久位置的引用，可复现性弱于入库。
- 解释性 ADR 不修改宪法正文，后续若有人按字面理解第 2.3 条，仍可能要求素材入表——本条是唯一挡板，须在评审中被引用。
