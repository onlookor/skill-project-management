## assumption 协议

**权威关系**：本文件是执行层文件。它落实 `CONSTITUTION.md` 第 6 条（`assumption` 的地位）与 `AGENTS.md` 第 5 条（输出结构约定）。

### 1. assumption 的两种合法用途

`CONSTITUTION.md` 第 6 条规定 `assumption` 不是成文法的一部分，不得被规则引用，不得编译为阻断性检查。但 `assumption` 有两种合法用途，二者的验证条件形态不同：

**用途 A：保守假设**（信息不足时的取值纪律）
当决策所需的事实缺失、且无法在决策前补齐时，取一个保守方向的值（对风险取上界、对能力取下界），并记录该假设与**可推翻指标**（什么观测值出现时该假设应被重审）。
**验证条件形态**：可推翻指标（一个可观测的量 + 阈值 + 观测方式）。
**典型场景**：`GRAMMAR.md` 的 G-F 组、G-G 组在核验完成前的 `assumption` 状态；接口契约中领域技能未填充的槽位。

**用途 B：待对齐映射**（两个体系之间的关系尚未确认时的显式声明）
当本技能的某个概念与外部体系（如某个领域技能提供的本体、某个外部框架）的对应关系尚未经原文核验时，该对应关系以 `assumption` 形式存在，不冒充已确认事实。
**验证条件形态**：对齐条件（与哪个外部文档的哪一节一致，或经哪个来源核验）。
**典型场景**：领域本体映射（软件工程语境见 `INTERFACE_CONTRACT_SPEC.md` 第 7 节）；`CHARTER.md` 承诺 C4 中提到的“可选插件的语义扩展”。

**判别规则**：若假设的内容是“一个数值/取值/方向”，属用途 A；若假设的内容是“A 与 B 是同一回事/存在对应关系”，属用途 B。

### 2. 区块格式

`assumption` 区块的每条假设必须包含以下字段：

```
assumption = {
  id:               // 唯一标识，格式 A-{批次}-{序号}
  statement:        // 假设的陈述（一句话，不得模糊）
  purpose:          // A（保守假设）| B（待对齐映射）
  basis:            // 为什么需要这个假设（缺什么事实/待对齐什么）
  verification: {   // 验证条件（按用途不同，字段不同，见第 3、4 节）
    ...
  }
  scope:            // 该假设适用于哪些活动/产物
  expires_at:       // 到期条件（见第 6 节）
  grounding_ref: null   // 强制为 null
}
```

**强制约束**：

- `grounding_ref` 必须为 `null`。任何非 null 值即违反 `CONSTITUTION.md` 第 6 条。
- `statement` 不得使用模糊措辞（“大致”“可能”“一般来说”）。模糊陈述无法被验证，不构成合法的 `assumption`。
- `verification` 不得为空。无验证条件的假设不构成合法的 `assumption`，只能构成“未处理的信息缺口”，后者必须被显式登记为待勘察项，而不是包装成假设。

### 3. 用途 A（保守假设）的验证条件

```
verification = {
  type: "refutable_indicator",
  indicator:        // 可观测的量（谓词/指标名）
  threshold:        // 阈值（含比较方向）
  observation:      // 观测方式（谁、何时、以什么频率观测）
  on_trigger:       // 指标命中时的动作（重审提议 / 升级 / 重新取值）
}
```

**编写规范**：

- `indicator` 必须是已登记的可观测谓词或指标，不得是新发明的、无法观测的量。
- `threshold` 必须有出处或明确说明为“注册表默认值”；无出处的阈值按 `GRAMMAR.md` 的约束纪律处理（不得伪装为精确值）。
- `on_trigger` 必须是可执行的动作，不得是“届时再议”。

**示例**（G-F4 时间证据的保守假设）：

```
{
  id: "A-F4-01",
  statement: "本项目里程碑间隔按 4 周估算，依据为团队历史节奏的保守上界",
  purpose: "A",
  basis: "问题空间未提供里程碑节奏的量化依据；估算方法条目待方法注册表填充",
  verification: {
    type: "refutable_indicator",
    indicator: "实际里程碑间隔中位数",
    threshold: "> 6 周（注册表默认阈值）",
    observation: "每个里程碑完成时由项目经理记录，月度汇总",
    on_trigger: "触发 G-F4 重新评估；升级为正式进度基线修订"
  },
  scope: "本项目的进度计划",
  expires_at: "首个里程碑完成后"
}
```

### 4. 用途 B（待对齐映射）的验证条件

```
verification = {
  type: "alignment_check",
  target_document:   // 待对齐的外部文档标识
  target_section:    // 具体章节/条款
  alignment_criterion: // 判定“一致”的标准（结构同构？语义等价？包含关系？）
  on_mismatch:       // 不一致时的动作（修订本技能 / 修订映射 / 放弃映射）
}
```

**编写规范**：

- `target_document` 必须是可访问的文档（本地优先，见 `AGENTS.md` 第 1 条）；不可访问的文档不构成合法的对齐目标。
- `alignment_criterion` 必须明确：是“结构同构”（两边的元素一一对应）、“语义等价”（两边的含义相同但结构可不同），还是“包含关系”（一边是另一边的特化）。
- `on_mismatch` 必须是可执行的动作。

**示例**（三空间映射）：

```
{
  id: "A-SP-01",
  statement: "本技能的约束分类（目标/环境/方案）与软件工程技能的三空间（问题/事实/解）存在对应关系：目标↔问题空间、环境↔事实空间、方案↔解空间",
  purpose: "B",
  basis: "三空间本体与 SE 技能严格绑定；本技能不依赖它，但需要声明对应关系以支持可选集成",
  verification: {
    type: "alignment_check",
    target_document: "软件工程元框架成文法（SE 技能）",
    target_section: "三空间本体论相关章节",
    alignment_criterion: "语义等价：三空间的“核心问题”与认识论方法与本技能三类约束的适用条件一致",
    on_mismatch: "修订本技能的三类约束定义，或放弃该映射并退回通用分类"
  },
  scope: "接口契约中的约束分类槽位；仅在宿主启用三空间插件时生效",
  expires_at: "与 SE 技能原文对齐核验完成时"
}
```

### 5. 三值逻辑与 unknown 的保守方向

检查条件求值遇 `unknown`（输入缺失、事实不可得）时：

**统一原理**：`unknown` 时，默认值必须选向**避免不可逆错误**的一侧。具体方向由场景决定：

| 场景 | unknown 的处置 | 理由 |
|---|---|---|
| 候选集装配（某候选的适用性谓词未知） | **保留候选**，附勘察义务 | 排除候选是不可逆伤害（好方案被静默丢弃） |
| 约束激活（某条件硬约束的激活条件未知） | **保守激活**，附勘察义务 | 约束静默失活是安全幻觉（违例事实已创造） |
| 槽位填充（某槽位值未知） | **阻断**，报告缺失项 | 槽位缺失时不做推断；推断即幻觉 |
| 检查项输入缺失 | **`cannot_evaluate`**，不当作 `pass` | 缺失输入当作通过是治理漏洞 |

**登记**：以上四条是 `ASSUMPTION_PROTOCOL.md` 的统一纪律；`GRAMMAR.md` 与 `COMPILATION_SPEC.md` 中涉及 `unknown` 的条款均引用本节。

### 6. 到期条件

每条 `assumption` 必须有 `expires_at` 字段，取值形态：

- **事件锚定**（优先）：某个可观测事件发生时到期（如“首个里程碑完成后”“与 SE 技能原文对齐核验完成时”）；
- **期限锚定**：某个日历日期到期（用于无法事件锚定的场景）；
- **永久**：仅当假设的内容在技能生命周期内不会变化时允许，且必须附理由。**“永久”不得用于保守假设（用途 A）**，只可用于待对齐映射（用途 B）中已被明确接受为长期存在的对应关系。

**到期处置**：

- 用途 A 到期：重新评估。若可推翻指标已命中 → 触发重审提议；若未命中 → 延长并更新 `expires_at`（延长本身是 `assumption` 的更新，不是新假设）。
- 用途 B 到期：执行对齐核验。核验完成 → 映射转为 `grounded`（若一致）或修订/放弃（若不一致）。
- 到期未处置 → 登记为执行层缺陷；持续未处置 → 升级为治理层议题（走 ADR）。

### 7. 与 grounded 的物理分离

输出中 `grounded` 与 `assumption` 必须是**物理分离的区块**，不得混排：

```
## grounded
- 命题 1（grounding_ref: SOURCE_LEDGER-ID）
- 命题 2（grounding_ref: SOURCE_LEDGER-ID）

## assumption
- A-XXX-01: 陈述（purpose: A/B，verification: ...）
- A-XXX-02: 陈述（...）
```

**禁止事项**：

- 把 `assumption` 写进 `grounded` 区块；
- 把 `assumption` 当作事实前提继续推理（`assumption` 只能作为“在验证条件满足前的暂定前提”，且推理链必须显式标注“依赖 A-XXX-01”）；
- 在 `assumption` 区块省略验证条件；
- 在 `grounded` 区块引用 `assumption` 作为依据。

**引用纪律**：任何 `grounded` 命题若依赖某条 `assumption`，必须显式标注依赖关系，且该命题的结论强度降级为“条件性结论”。条件性结论不得作为阻断性检查的依据。

### 8. 在编译产物中的表示

`COMPILATION_SPEC.md` 第 4 节规定：规则状态为 `assumption` 的检查项，编译产物中必须携带 `assumption_basis` 字段，指向 `GRAMMAR.md` 中对应规则的 `assumption_verification`。该字段的语义是：

- 该检查项的形式化依据尚待核验；
- 校验器输出必须携带 `rule_status: assumption`；
- 宿主据此决定仅记录而不阻断；
- 生成模型转述时不得把该检查项的 `fail` 说成“违规”，只能说“未满足（假设级）”。

### 9. 不做的事

- 不把无来源断言包装成 `grounded`；
- 不把 `assumption` 当作永久豁免；
- 不用“业界共识”“最佳实践”作为 `assumption` 的 `basis`（`basis` 必须说明缺什么事实或待对齐什么）；
- 不在 `verification` 中写“届时再议”；
- 不把用途 A 的假设写成“永久”；
- 不把 `assumption` 转述为事实。
