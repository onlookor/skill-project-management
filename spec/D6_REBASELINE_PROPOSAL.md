## 1. 结论摘要

1. **现行设计的核心产物是"项目管理产物的合规检查器"，不是"完成项目管理任务的能力"**。现状可执行的东西只有两类：对 17 条规则做判定的检查器原型（`validation/checker-prototype/checker.py`，68 个样例），和治理自检脚本。【事实】新目标要求的是"任务从输入走到产出"，两者相差一整层：**没有任务目录、没有工序定义、没有产出工件 schema、没有模板**。
2. **"技能承担判断"只在分档意义上成立**。把 42 项原子能力逐条判定后：11 项可完全机械化；18 项是"机械骨架 + 模型填槽"；13 项含人类签字；**0 项是"纯模型自由推理且无人负责"**。【推断，依据第 3 节】因此 D6 应当改写为"技能把可机械部分做到极致、判断部分显式外置"，而不是宣称"不需要强模型"。
3. **为"编译接地"建立的大部分资产在新目标下不是失去必要性，而是位置错了**。来源登记、锚点、指纹、缺口台账属于**维护期**资产，运行期不加载；它们对 D6 的贡献只有"口径可辩护"，没有"任务可完成"。当前路线把 M2 放在关键路径（M0→M1→M2→M7）、把 M3/M4 作为里程碑主体，这是与新目标最大的错配。【事实：`ROADMAP.md` 关键路径行 + 推断】
4. **309 条本体定义、92 类、24 条 SHACL 形状在运行期消费者为零**：`GRAMMAR.md`、`spec/`、`validation/`、`contracts/`、`knowledge/` 中对 `pmbok8:` IRI 的引用数为 0。【事实，命令见附录 B】它们可以被保留为可检索档案，但不应继续作为里程碑主线；继续扩写的边际收益接近零。【推断】
5. **D6 目前不可判真假**。缺三样东西：基准模型档位、任务集与评分规则、达标阈值。在此之前 D6 只能记为"未验收"，且 `v1.0.0` 的发布门槛（只列 D1–D5）不包含 D6——即当前体系允许"在最高目标未验收的情况下宣布 v1.0.0"。【事实 + 推断】
6. **建议的重基线**：把"任务目录 + 工序 + 工件 schema + 校验入口"作为新的能力层，把既有 17 检查/41 子句/68 样例原样收编为校验层核心，把来源/锚点/本体/缺口台账降为维护期档案，并用"弱模型 × 任务集 × 控制臂"的基准作为 D6 唯一验收出口。

## 2. 需求层

### 2.1 目标陈述

**G0（上位目标，用户原话意图）**：agent 挂上本技能即可完成各类项目管理任务，且不依赖背后超大规模参数模型的即兴能力——流程、口径、任务分解与校验由技能承担。

**G0 的可判真假化（提案）**：把"不依赖即兴能力"拆成四个可分别核对的分目标。这一拆分的理由：G0 原文把"完成任务"和"不由模型补足"绑在一句话里，任何一个都可以单独不成立，混在一起就无法定位失败原因。

| 编号 | 分目标 | 为什么必须单列 | 可核对的形态 |
|---|---|---|---|
| G0-a | **流程由技能给出**：任务从输入到产出有固定工序，不由模型临场编排 | 否则"挂上即可"取决于模型的规划能力 | 任务目录中每类任务的工序可被逐条执行并产出指定工件 |
| G0-b | **口径由技能给出**：术语、判据、阈值、枚举有唯一出处，运行期可按键检索 | 否则同一问题两次回答不一致 | 运行期口径字典覆盖工序引用的全部术语；同一输入两次运行结论一致 |
| G0-c | **分解由技能给出**：WBS、工序、检查项的结构由技能规定，模型只填内容 | 否则弱模型无法稳定产出结构化结果 | 工件 schema 强约束 + 机械完备性校验 |
| G0-d | **校验由技能给出且不由模型执行**：结论来自确定性程序 | 否则"检查通过"不可信 | 校验入口为程序；模型不得输出 `pass` |

**G0 与"不依赖强模型"的关系**：G0-d 与 G0-a 可以让"过程正确性"脱离模型规模；G0-b 可以让"一致性"脱离模型规模；但**内容的具体质量（例如是否识别出真正的关键风险）不可能脱离模型能力**——它只能被"外置给人类"或"用模板与清单降低难度"。这是本提案要求改写目标表述的唯一理由，见 7.1。

### 2.2 使用者与使用场景

| 角色 | 场景 | 现在能做到吗 | 依据 |
|---|---|---|---|
| 弱模型 agent（≤7B） | 接到"给这个项目做 WBS"的任务，需要知道先问什么、按什么结构产出、产出后自检 | **不能**。技能提供 5 条方法条目（每条 5–8 步的一句话）与 17 条检查规则，但没有任何产出结构、没有工序卡、没有模板 | 【事实】`knowledge/methods/registry-skeleton.md` 仅 5 条；`spec/CONTEXT_ASSEMBLY.md` 的加载集是"读哪些文档"，不含工序与模板 |
| 强模型 agent | 同上 | 能做出结果，但**是否用了技能无法区分**：技能没有留下"按工序执行"的证据格式 | 【推断】现有证据工件只有检查记录与装配清单 |
| 人类项目经理 | 用技能审计一个已有项目产物 | **部分能**，限 17 条规则的判定面 | 【事实】`validation/CHECKLIST.md` 17 行 |
| 人类责任方 | 批准高影响决策 | 能，但技能只定义"必须有 Accountable"，没有定义"批准要看到什么" | 【事实】G-E1 只检查问责结构存在，不检查批准材料 |
| 部署方 | 判断"这个技能挂上了没有" | 能，按 `spec/GROUNDING_CRITERIA.md` 六条；但六条验证的是产物自洽，不是任务能力 | 【事实】G1–G6 全部指向规则/编译/术语/装配，无一条指向任务完成 |

**结论**：现行使用者定义（`CHARTER.md` 第 2 条：首要服务对象是"知识不足的本地小模型"）与新目标一致，但**服务方式错位**——现在服务的是"让模型别记错规则"，新目标要求的是"让模型能做完任务"。

### 2.3 验收判据（D6 怎么量）

**D6 的验收需要且只需要三样东西**，缺任一项即只能记"未验收"：

| 要件 | 内容 | 为什么缺它就不能验收 | 当前状态 |
|---|---|---|---|
| V1 基准模型 | 至少两档：弱档（本地 ≤7B 量化）、对照档（同一技能 + 强模型） | 没有弱档，"不依赖强模型"无法测量；没有对照档，无法区分"技能起作用"与"任务太简单" | 未定 |
| V2 任务集 | ≥30 个任务，覆盖第 3 节的能力域；每个任务给输入事实、期望产出结构、可机械判定的失败项与需人评的项 | 没有固定任务集，通过率不可比、可挑选有利样本 | 未定 |
| V3 达标判据 | 两个数：机械项通过率阈值、人评项通过率阈值；外加一条控制臂差值要求（有技能 − 无技能 ≥ 某值） | 只有绝对通过率，无法排除"模型本来就会"；只有差值，无法排除"两边都不可用" | 未定 |

**控制臂（必须写进判据）**：同一模型、同一任务集、去掉技能（不给任务卡/工序/schema）跑一遍。理由：D6 主张的是"能力由技能承担"，没有差值就无法证明归属。【推断】这是本提案对 D6 唯一的实质性加固。

**在没有 V1–V3 时的诚实表述**：D6 状态为 `未验收`；技能不得对外声称"已被证明可由小模型完成项目管理任务"；`v1.0.0` 若在此前发布，发布说明必须写明该目标未验收。

## 3. 能力分解

### 3.1 判定口径

把"各类项目管理任务"拆成原子能力，逐条判定五档之一。分档不是按"难不难"，而是按**失败时能否被机器指出**：

| 判定 | 含义 | 入档条件 |
|---|---|---|
| **M** | 可完全机械化 | 输入确定后输出唯一，或用图算法/算术/枚举/阈值即可判定正确性；模型可以不参与 |
| **M+J** | 机械骨架 + 模型填槽 | 结构、字段、数量、关系、完备性由技能规定并可机械校验；**内容取值**由模型给出，且可被"字段级格式/枚举/引用"约束 |
| **M+J+H** | 上述 + 人类签字 | 填槽结果会改变承诺、预算、责任或外部义务，必须有人署名 |
| **M+H** | 机械骨架 + 人类签字（内容由人给） | 内容无客观来源，只能由责任方决定（如批准、责任分配） |
| **J+H** | 无机械骨架，模型提议 + 人裁定 | 需要领域/情境推理，且失败后果不可由结构校验发现（如赶工方案、纠正措施） |

**"H" 的含义**：不是"人帮忙填表"，而是**技能负责把决定做成不可回避的关口**（列出必须看到的证据、记录署名、缺失即阻断）。技能承担的仍是机械部分。

### 3.3 分档统计与结论

| 判定 | 数量 | 占比 | 含义 |
|---|---|---|---|
| M | 11 | 26% | 技能可完全承担，模型不参与也不影响结论 |
| M+J | 18 | 43% | 技能承担结构与校验，模型只填内容 |
| M+J+H | 4 | 10% | 以上 + 必须有人署名 |
| M+H | 6 | 14% | 内容由人给，技能只把关口与材料 |
| J+H | 3 | 7% | 模型提议、人裁定，技能只能保证留痕 |
| **合计** | **42** | 100% | |

**结论 1：42 项全部都有机械部分**，没有一项是"完全交给模型即兴"。这支持 G0 的前半句（流程、口径、分解、校验由技能承担），但支持的方式是"技能给出骨架并兜底"，不是"技能替模型思考"。【推断】

**结论 2：可完全机械化的只有 11 项，且集中在"算法能算出唯一答案"的地方**（依赖图、关键路径、挣值、汇总、结构校验、合规判定、一致性、留痕）。这些恰好是现行 17 条规则覆盖的领域——**说明已有资产是对的，但只覆盖了 26% 的能力面**。【推断】

**结论 3：43% 的能力（18 项）落在"机械骨架 + 模型填槽"**。这是本提案认为唯一可规模化的路径：**把生成任务改造成填表任务**。它成立的前提是工件 schema 足够严（枚举、必填、引用、数量约束）且校验足够细；否则"填槽"退化成自由生成，弱模型立刻失效。【推断】

**结论 4：31% 的能力（13 项）含人类签字**。这不是缺陷：项目管理的产出本来就包含承诺与责任。但现行体系只检查"是否存在 Accountable"（G-E1），没有规定"签字前必须看到什么"，导致签字可能流于形式。【事实 + 推断】

**结论 5（对目标表述的直接后果）**：D6 若保持"不依赖超大规模参数模型的即兴能力"这一原话，则只能对 11 项 M 能力成立、对 18 项 M+J 部分成立、对 13 项 H 不适用。因此必须改写为："技能使 26% 的能力完全脱离模型；使 43% 的能力降为受约束的填槽；使 31% 的判断显式外置并留痕。"

### 3.4 三种失败模式（本提案要求在设计里显式防住）

| 失败模式 | 表现 | 为什么危险 | 防线 |
|---|---|---|---|
| F1 把"有模板"当机械 | 只给模板不校验，模型随便填也能过 | 弱模型产出看似合规、实则空洞 | 每个模板必须绑定≥1 条完备性校验；无校验的模板不得发布 |
| F2 把"模型填槽"当机械 | 声称"技能承担分解"，实际由模型自由生成结构 | 结构漂移，检查器无法核对 | 结构必须由 schema 固定，模型只能填值；结构字段不得由模型新增 |
| F3 把签字当流程装饰 | 有签字位但无材料清单，签了也不知道批什么 | 责任形式化，审计无效 | 每个签字点必须有"必须看到的证据"清单，缺项阻断 |

## 4. 架构提案

### 4.1 分层

现行架构的四层（规则／编译／知识／治理）是按"让规则可接地"组织的；新目标按**"运行时需要什么"**组织。提案分五层，关键区别是新增 L1 **运行契约层**，并把原"编译/治理"整体移入 L4 档案层。

```
L1 运行契约层   task-catalog / procedures / artifact schemas / approval gates   ← 新增，运行期必载
L2 校验层       pm_check 入口 + 结构/完备/跨工件/17 规则                           ← 由现有 checker 改造
L3 知识与口径层 runtime bundle: 口径字典 + 方法卡 + 模板                            ← 由 CONTEXT_ASSEMBLY 改造
L4 档案层       本体 92 类 / 309 定义 / SHACL / 来源登记 / 锚点指纹 / 缺口台账       ← 维护期，运行期不载
L0 治理层       CONSTITUTION / ADR / 发布门槛 / 钉扎                               ← 不变，但门槛缩减
```

**为什么要单列 L1**：没有 L1，"挂上即可"只能靠模型的规划能力，等于把 G0-a/G0-c 交还给模型。L1 是唯一能让弱模型"知道下一步做什么"的东西。【推断】

**为什么 L4 仍然存在但不进运行期**：来源、锚点、本体的价值是"口径可辩护、维护可追溯"，服务对象是维护者与审计者，不是运行时模型。把它们加载给弱模型只会挤占上下文且不产生任务产出。【推断，与 `spec/CONTEXT_ASSEMBLY.md` 第 1 节"不加载档案"一致】

### 4.2 组件职责

| 组件 | 职责 | 运行期 | 失败行为 |
|---|---|---|---|
| `runtime/task-catalog.yaml`（计划创建） | 任务类型清单：任务名、适用条件、输入槽、输出工件、绑定工序、绑定校验、签字点 | 是 | 任务不在目录 → 拒绝执行并报告"未支持"，不得现场发明流程 |
| `runtime/procedures/*.yaml`（计划创建） | 工序卡：有序步骤，每步仅允许 6 种算子 | 是 | 步骤算子越界 → schema 校验失败；步骤缺产出 → 阻断 |
| `runtime/artifacts/*.schema.json`（计划创建） | 工件结构与字段约束（枚举/必填/引用/数量/区间） | 是 | 工件不合 schema → 不进入 L2 |
| `runtime/templates/*.md`（计划创建） | 只含结构与占位，不含示例内容 | 是 | 模板未绑定校验 → 发布检查失败 |
| `runtime/glossary.jsonl`（计划创建） | 口径字典：术语、判定规则、枚举值、公式 | 是 | 术语未登记 → 报告 `undefined-term` |

| `scripts/pm_check.py`（计划创建） | **唯一校验入口**：`--artifact <type> --file <path>` | 是 | 退出码固定语义（见 4.5） |

### 4.3 运行期契约

三类契约，全部是**可机读**的；这是本提案认为"D6 可验收"的技术前提。

**(1) 任务契约**

```yaml
task: wbs_breakdown
version: 1
inputs:   {charter: ProjectCharter, scope_constraints: ConstraintSet}
preconditions: [charter.check_A1 = pass]
steps:
  - {id: S1, op: fill_schema, schema: wbs.node, produces: wbs_tree}
  - {id: S2, op: compute,    method: wbs.rollup, produces: wbs_rollup}
  - {id: S3, op: check,      checker: wbs.structure, fails: block}
  - {id: S4, op: human_approve, gate: scope_baseline, evidence: [S1, S2, S3]}
outputs: [wbs_tree, wbs_rollup]
checks:  [wbs.children_cover_parent, wbs.package_grain, wbs.code_unique]
```

**算子闭集（6 个）**：`fill_schema`、`compute`、`lookup`、`check`、`human_approve`、`render`。理由：闭集使得"模型是否按工序执行"可被机械核对；一旦允许模型自造算子，工序就不再约束流程。【推断】这是防止 F2 的主要手段。

**(2) 工件契约**

```json
{
  "type": "wbs.node",
  "required": ["id", "parent", "title", "deliverable_ref", "owner_role"],
  "properties": {
    "grain_hours": {"type": "number", "minimum": 8, "maximum": 80},
    "children_cover": {"const": "all_parent_scope"}
  },
  "x-checks": ["wbs.children_cover_parent", "wbs.package_grain"],
  "x-provenance": {"requires": ["charter.goal", "constraint.id"]}
}
```

`x-checks` 是强制字段：**没有绑定校验的 schema 不得进入运行期**（防 F1）。`x-provenance` 要求每个内容字段可指回输入，防止模型无源生成。

**(3) 签字契约**

```yaml
gate: scope_baseline
approver_role: sponsor
must_see: [wbs_rollup.total_hours, risk.top5, constraint.coverage_report]
record: approval.jsonl {actor, role, decision, seen[], ts}
on_missing_evidence: block
```

`must_see` 是 F3 的防线：签字前必须看到的证据是固定清单，不可由模型选择。

### 4.4 数据与知识层形态

| 资产 | 形态 | 大小约束（提案） | 理由 |
|---|---|---|---|
| 口径字典 | JSONL，一行一术语：`{term, def_cn, rule, enum, formula, source_id}` | 单条 ≤ 200 字；运行期合计 ≤ 60 KB | 弱模型上下文有限；只装被工序引用的术语 |
| 方法卡 | Markdown，固定四段：公式/算法、输入、输出、失效条件 | 单卡 ≤ 1 页 | 现行 5 条方法只有"一句话步骤"，不可执行 |
| 工件模板 | Markdown，只有结构与占位 | 单模板 ≤ 1 页 | 含示例会诱导模型照抄 |
| 任务卡 | YAML（4.3(1)） | 单卡 ≤ 80 行 | 控制装配体积 |

**运行期装配预算（替换 `spec/CONTEXT_ASSEMBLY.md` 的 S1–S4）**：任务卡 1–2k + 工序卡 1–2k + 相关 schema 2–3k + 模板 1k + 口径子集 1–2k ≈ **6–10k tokens**。与该文档现有 S3（8–18k）相比更小，但内容完全不同：现在是"读哪些规范文档"，提案是"执行这个任务需要什么"。【推断】此预算需在 R4 用真实模型实测校准，不能直接采信。

**不引入向量检索**：术语与规则按 key 精确检索即可；语义相似检索会引入不可复现的召回差异，与"同一输入两次结论一致"的 G0-b 冲突。【推断】

### 4.5 校验层的边界与信任模型

**能机械判定的**（可写进 `pm_check`）：

| 类别 | 例 |
|---|---|
| 结构 | 必填字段、类型、枚举、区间、编码唯一 |
| 引用 | 跨工件 ID 是否存在、集合是否覆盖、是否有孤儿 |
| 计算 | 汇总守恒、公式复算、关键路径、挣值 |
| 一致性 | 承诺↔交付物↔断言↔变更 |
| 规则 | 现有 17 条规则及其 41 条子句 |

**不能机械判定的**（必须在产物中显式标 `unsupported`，不得默认通过）：

| 类别 | 例 | 只能靠什么 |
|---|---|---|
| 语义忠实 | "这条风险描述是否真的对应这个项目" | 非同源复核 / 人评 |
| 内容真实性 | "估算的单价是否是市场价" | 外部数据源 |
| 质量优劣 | "这个 WBS 拆得好不好" | 人评 |
| 责任适当 | "这个人是否适合当 Accountable" | 签字 |

**信任模型（三句话）**：
1. **机械结论可自证**：任何人重跑同一入口应得同一结论；不能复现的结论视为无效。
2. **结构结论只能证"不违规"，不能证"正确"**：schema 通过只说明形状对。
3. **语义结论不可自证**：只能由非同源复核、人类签字或真实运行数据承接；钉扎与指纹只能**检测漂移**，不能证明正确。

**退出码语义（固定，不可由模型解释）**：

| 码 | 含义 | 使用条件 |
|---|---|---|
| 0 | 全部适用检查通过 | 且不存在 `unsupported` 项 |
| 1 | 存在违规 | 有明确违规项 |
| 2 | 输入不合法（缺槽/类型错） | 工件未过 schema |
| 3 | 存在无法机械判定的项 | 产物已标 `unsupported` 清单 |
| 4 | 检查器自身不可用 | 版本/依赖缺失 |

`3` 是关键：它让"没验"变成一等公民，避免现行体系里"未复核静默通过"的老问题（`GAP_LEDGER.md` G-017 的实测症状）。

### 4.7 最小端到端示例（说明各层如何咬合）

任务：`wbs_breakdown`（CAP-08/09，判定 M+J）。

1. L1 任务卡给出输入槽（章程、范围约束）与前置检查（A1 通过）。
2. L3 装配：任务卡 + 工序卡 + `wbs.node` schema + WBS 模板 + 口径子集（工作包、100% 规则、粒度区间）。
3. 模型只做 `fill_schema` 一步：按 schema 填树节点；结构由 schema 决定，模型不能新增字段或层级规则。
4. L2 依次执行：结构校验（schema）→ 覆盖性（子项并集 = 父项范围）→ 粒度区间 → 编码唯一 → 跨工件引用（交付物存在）。
5. 任一失败返回 `1` 并给原因码；全部通过但存在"拆分质量"未评项则返回 `3`，同时输出 `unsupported` 清单。
6. 进入 `scope_baseline` 签字关口：必须看到汇总工时、覆盖率、前 5 风险；缺项 `blocked`。

这一条链里，模型只贡献第 3 步的内容；流程、结构、覆盖性、粒度、引用、关口全部由技能承担。这正是 G0 想要的形态。

### 8.6 专项：挣值与成本口径是否必须引 PMI

**结论：不必。** 理由与条件如下。

(1) **付费物不可作为核对依据**。PMI《Practice Standard for Earned Value Management》与 ANSI/EIA-748 均需购买；按 `CONSTITUTION.md` 第 2.5 条，未核验的内容不能作为核对依据，因此它们至多能出现在 `provenance_note` 里作为"上游来源名"，不能作为 `claim_mapping` 的锚。

(2) **公开等效物已覆盖同一套内容**（均为 2026-11-15 公开检索所见，标【待核验】的部分需下载全文核对）：

| 文件 | 性质 | 覆盖 | 核验状态 |
|---|---|---|---|
| GAO-20-195G《Cost Estimating and Assessment Guide》 | 政府审计机构指南，有版本号 | EVM 定义与指标、成本估算可靠性、WBS—成本映射 | 在线可读，章节页已见【待核验：全文公式】 |
| NASA《EVM Reference Guide for Project-Control Account Managers》(NTRS 20200000301) | 政府机构公开 PDF | EIA-748 的 32 条准则映射、WBS 与挣值关系 | 公开 PDF 可下载【待核验】 |
| NASA《EVM Implementation Handbook》(NTRS 20180001499) | 政府机构公开 PDF | 实施要求、与 EIA-748 的合规路径 | 公开 PDF 可下载【待核验】 |
| DOE G 413.3-10A《Earned Value Management System》 | 政府机构指南，有编号 | 以 ANSI/EIA-748-B 为认证基准的实施与审查 | 公开 PDF 可见【待核验】 |
| AACE RP 82R-13《EVM Overview and Recommended Practices Consistent with EIA-748-C》 | 行业协会推荐实践，有编号 | 与 EIA-748-C 对齐的实践与输出物 | 公开 PDF 可见【待核验：使用许可】 |

(3) **能否过 `CONSTITUTION.md` 第 2.6 条**：能，但必须按下面三条落地，否则会被第 1 条"领域测试"拦下：
- **以章节为对象，不以整份文件为对象**。`allowed_uses` 只写 EVM 公式/术语/32 准则映射，明确排除政府采购条款、合同条款、机构内部流程（这些属特定领域实践）。
- **一项能力只固定一个主源**。EAC 三法在不同文件中并存，必须指定"本技能采用哪一源的第几式"，其余只作对照；跨源混用即为口径分叉。
- **在 `provenance_note` 记录与 EIA-748 准则编号的对应关系**，并声明"EIA-748 原文未核验（付费），仅核验其公开转述"。这满足第 2.5 条的诚实义务，不构成对未核验内容的引用。

(4) **仍然存在的差异**：政府文件惯用 BCWP/BCWS/ACWP 旧称，PMI 用 EV/PV/AC。口径字典必须固定一套并给出别名映射，否则同一工件会出现两套指标名。

### 8.7 结构问题：案例素材该不该进 `SOURCE_LEDGER.md`

**先给判定依据**（原文要点）：
- 第 2.1 条：入表须满足三条件之一——公开发布的标准或规范 / 同行评议或可检索的学术本体 / 技能已接受的上游本体。
- 第 2.6 条：先过领域测试（通用项目管理），再过落点测试，落点只能是 `rule:` / `knowledge:` / `method:` / `check:`，否则只能 `pending:<TODO>`。

**判定**：案例素材**两条都不满足**。它不是标准、不是本体；它的用途是提供任务输入与真实数字，不支撑任何规则或术语，因此拿不到合法落点。若强行入表，只能写 `pending:`，等于在口径表里放一条永远无法闭合的条目——正是 G-017 那类问题的翻版。

**三个选项**：

| 选项 | 做法 | 是否需修宪 | 代价 | 风险 |
|---|---|---|---|---|
| A 另立"案例素材"登记类别 | 在来源体系内新增一类条目与独立测试 | **需要**（2.1 的入表条件与 2.6 的落点枚举都要改） | 一次修宪 + 检查器改造 + 每案一条 ADR | 口径表被数据淹没；`authority_tier` 语义被稀释 |
| B 不入表，只做本地素材（建议） | 素材放 `validation/cases/`（计划创建），配一份 MANIFEST 记录来源、许可、获取日期、改造说明、服务哪个任务 | **不需要** | 追溯靠 MANIFEST 纪律，非机械 | 清单可能漏记；无检查器兜底 |
| C 入表并逐案豁免 | 在表内加豁免标记 | **需要** | 同上且更重 | 豁免先例一开，2.6 形同虚设 |

**建议：B。** 并附一条**解释性 ADR**（不改条文）：第 2.3 条"本地 `resources/` 目录中确实存在副本的来源应被认可入表"，其对象是**规范来源**，不适用于作为任务输入的数据素材；因此案例素材不得放入 `resources/`，一律放 `validation/cases/`。这样既不触发 2.3，也不需要修宪。

**分界规则（关键）**：
- 案例作为**任务输入**（事实、数字、背景）→ 不入表，走 MANIFEST。
- 由案例或评审清单抽象出的**评分判据**（如"成本估算是否可追溯"）→ 属口径，按 RG-15 入表，落点写 `check:` 或 `method:`；**案例本身仍不入表**。

**代价**：B 放弃了对素材的机械可追溯。若将来要补，只需一个校验 MANIFEST 字段完整性的小脚本，仍不需修宪；这是三个选项里唯一"可逆"的。

### 8.8 本节三条结论

1. **资料缺口不是主要瓶颈**：16 条中 9 条可公开获得（A+B），4 条属自研，真正"拿不到"的只有偏差阈值与状态采集口径（RG-09/10）——它们是责任缺口，不是资料缺口。
2. **挣值不必引 PMI**：GAO-20-195G、NASA 两本 EVM 手册、DOE G 413.3-10A、AACE 82R-13 公开可核，按"章节为对象 + 单一主源 + 记录 EIA-748 映射"三条即可过 2.6；代价是必须放弃"多源公式并用"的自由。
3. **案例素材不进 `SOURCE_LEDGER.md`**：它同时不满足 2.1 与 2.6；建议走 B（`validation/cases/` + MANIFEST + 一条解释性 ADR），只有由案例抽象出的评分判据才入表。A 与 C 都要修宪，均不建议。
