# 治理结构改造提案：引入计划层之后

**性质**：提案与影响评估。**非规范**。本文件不改变任何条文；第 4 节列出的改动在对应 ADR 被 `accepted` 之前不生效。它与 `spec/ONTOLOGY_FEASIBILITY.md` 同类——都是评估文档，不是规则。

**要解决的问题**：`ROADMAP.md` 引入了一个新的计划层。现有治理结构把“后续工作”全部压在 `TODO.md` 上，没有为“顺序、里程碑、出口条件、发布点”留位置。新层一旦存在，`TODO.md` 的“唯一登记处”表述、`AGENTS.md` 的目录权威、`STATE.md` 的状态口径都会与之产生重叠。本提案给出诊断、目标结构与两档落库方案，供批准。

## 1. 现状诊断

### 1.1 各文件现在管什么

| 文件 | 现在的事实职责 | 明确不负责 |
|---|---|---|
| `CHARTER.md` | 意图层：为什么存在、服务谁、承诺 C1–C6 及检查方式 | 规则内容、修改程序 |
| `CONSTITUTION.md` | 治理层：三权分立、来源封闭、自包含、插件、编译治理、术语治理、接地治理、原始资料禁令 | 具体工作项、文件状态 |
| `GRAMMAR.md` | 立法层：规则组 A–G，每条带的字段与检查标识 | 执行细节、优先级 |
| `SOURCE_LEDGER.md` | 立法层：封闭来源枚举、状态、权威层级、论断级映射、编译落点 | 工作项状态 |
| `GLOSSARY.md` | 立法（支撑）：术语定义与术语治理 | 工作项 |
| `spec/` | 执行层规范：编译元框架、装配、接地判据、锚点、方法声明、假设协议、接口契约 | 规则内容、计划 |
| `contracts/` | 执行层：槽位 schema、解析规则、领域样例 | 规则内容 |
| `knowledge/` | 知识层：本体条目与方法注册表 | 规范效力 |
| `ontology/` | 派生工件：自建本体与形状，非规范、非来源 | 作为 `grounding_ref` |
| `validation/` | 执行层：检查清单与反例用例 | 执行本身（由校验器执行） |
| `STATE.md` | 调度层：每个文件的**当前状态**，按目录默认值加例外，以 `git ls-files` 对账 | 历史、任务、计划 |
| `CHANGELOG.md` | 调度层：**已发生**的变更批次，append-only，禁止改写 | 未发生的事 |
| `TODO.md` | 调度层：**未完成的单点工作项**，含依赖与状态 | 顺序、里程碑、发布 |
| `ERRATA.md` | 调度层：已发现的错误、外部评审处置、待核验表述 | 计划 |
| `adr/` | 治理层：决策上下文与状态 | 规则文本、工作项状态 |
| `README.md` | 入口：定位、文件地图（导航指针）、阅读路径 | 任何权威 |
| `AGENTS.md` | 执行约定：资料获取、检查分工、schedule 纪律、**目录结构唯一权威** | 立法 |

### 1.2 权威边界中的重叠与留空

**重叠**：

1. `AGENTS.md` 的 3.2 同时要求“完成时移出 TODO”与“保留编号标 `[done]` / `[dropped]`”。两种做法在仓库里都出现过：T-070、T-108 等保留在正文并标 `done`；条文却没有说清哪种为准。
2. `CHANGELOG.md` 每个批次带“状态：生效 / pending-adr”，`STATE.md` 也有“当前状态”。前者是变更是否生效，后者是文件是否可用；名称相同、语义不同，容易被当成同一件事。
3. `TODO.md` 的“前置依赖”与“状态”都能表达“还不能做”，但没有区分“等内部完成”与“等外部条件”。

**留空**：

1. **谁定义顺序**：`TODO.md` 没有排序语义，`AGENTS.md` 也没有规定按什么排序。
2. **谁定义里程碑完成**：没有文件规定“里程碑关闭”的证据格式。
3. **谁定义发布节奏**：版本规则在 `CONSTITUTION.md` 第 9 条与 `manifest.json`，但没有“何时打 tag、由哪个工作项触发”的安排。
4. **计划变更由谁批准**：`AGENTS.md` 的目录权威没有覆盖计划文件。
5. **外部阻塞如何表达**：没有 `blocked-external` 状态，外部依赖项只能留在 `open`。
6. **计划中但尚未创建的文件如何登记**：`STATE.md` 以 `git ls-files` 对账，只能表达已存在的文件；T-117 这类“计划创建”的条目没有状态位置。

### 1.3 STATE vs CHANGELOG vs TODO vs 计划层

| 问题 | 应由谁回答 | 现在实际由谁回答 | 冲突点 |
|---|---|---|---|
| 这个文件现在能不能用 | `STATE.md` | `STATE.md` | 无 |
| 这个文件什么时候被改过 | `CHANGELOG.md` | `CHANGELOG.md` | 无 |
| 这件事做没做 | `TODO.md` | `TODO.md`，但完成项是否移出不确定 | 条文自相矛盾 |
| 先做哪件、做到什么算完 | 计划层 | **无人回答** | 新增 |
| 何时发布、发哪个版本 | 计划层 + `manifest.json` | 无人回答；`manifest.json` 只有当前值 | 新增 |
| 计划里的某条现在什么状态 | `TODO.md` | `TODO.md` | 需要规定计划层不镜像单点状态 |
| 计划中但尚未创建的文件 | 计划层（计划项）；`STATE.md` 不登记 | 无人回答 | 新增 |

**结论**：四者不是同一维度的四个副本，而是四个不同问题：**现状**（STATE）、**历史**（CHANGELOG）、**单点待办**（TODO）、**顺序与验收**（计划层）。当前冲突来自两点：`TODO.md` 被要求同时承担单点与顺序；`AGENTS.md` 没有为第四者留位置。

### 1.4 治理结构层本身的问题

| 编号 | 问题 | 具体表现 |
|---|---|---|
| G1 | 调度层没有位置 | `CONSTITUTION.md` 第 1 条的三权分立只有立法、治理、执行；`STATE.md`、`CHANGELOG.md`、`TODO.md` 不属于任何一权，靠 `AGENTS.md` 的“不构成立法”自治 |
| G2 | 第 4 条管辖范围不含调度层 | 实质性修改清单只列 `CHARTER.md`、`GRAMMAR.md`、`SOURCE_LEDGER.md`、本文件、编译元框架、接口契约；计划文件的增删没有程序 |
| G3 | 第 5 条第 2 项的“受影响对象”过窄 | 要求 ADR 引用 `GRAMMAR.md` 规则或 `SOURCE_LEDGER.md` 条目；纯治理结构调整（例如新增计划层）可能找不到自然对象，形成程序性死锁 |
| G4 | 目录结构权威与程序不匹配 | `AGENTS.md` 自称“不构成立法”，却掌握目录结构唯一权威；目录变化会改变 `STATE.md` 对账与检查器默认值，但不需要 ADR |
| G5 | 检查粒度未定义 | `check_state.py` 只核对文件是否存在与状态值；不核对计划、TODO、tag 之间的一致性 |
| G6 | 发布动作无归属 | `manifest.json` 与 tag 的一致性没有检查项（T-110），也没有发布责任人与触发条件 |

**保护清单的现状**：`CONSTITUTION.md` 第 5 条保护第 1、2、13、7、8 条与第 10 条援引的 P1–P6、方法准入条件、“可选择、可共存、可替换”约束。本提案**不修改保护清单，也不降低其中任何一项**。

## 2. 目标结构

### 2.1 层次与优先级

```
意图层      CHARTER.md
              │（承诺约束一切）
治理层      CONSTITUTION.md + adr/
              │（谁改、怎么改）
立法层      GRAMMAR.md + SOURCE_LEDGER.md + GLOSSARY.md
              │（规则与来源是什么）
执行层      spec/ + contracts/ + validation/ + knowledge/ + ontology/ + scripts/
              │（怎么执行、怎么判）
调度层      ROADMAP.md → TODO.md → STATE.md / CHANGELOG.md / ERRATA.md
              （先做什么、做到什么算完、现在怎样、发生过什么）
```

**优先级**：

1. 语义冲突依上位层：意图层 > 治理层 > 立法层 > 执行层。
2. 调度层**不产生规范语义**，不得用来解释或放宽任何规则；调度层内部冲突按 2.3 的单一事实来源裁决。
3. 保护清单的强度高于普通条文；任何降低保护清单的修改仍按第 5 条的现有程序处理。

### 2.2 每层唯一职责

| 层 | 唯一职责 | 不得承担 |
|---|---|---|
| 意图层 | 为什么存在、承诺什么 | 规则文本、修改程序、工作项 |
| 治理层 | 谁在什么条件下改什么、如何追溯 | 规则内容、执行细节 |
| 立法层 | 什么算合法的项目管理断言、来源是什么 | 执行方法、计划 |
| 执行层 | 把立法翻译为可运行的检查、装配与契约 | 规则内容、排序 |
| 调度层 | 顺序、验收、现状、历史 | 规范语义 |

### 2.3 单一事实来源与冲突裁决

| 问题 | 唯一权威 | 其他文件只能怎样引用 |
|---|---|---|
| 为什么做这个技能 | `CHARTER.md` | 引用，不改写 |
| 谁能改、怎么改 | `CONSTITUTION.md` + `adr/` | 引用 |
| 规则是什么 | `GRAMMAR.md` | 引用 `G-xN` |
| 来源是什么 | `SOURCE_LEDGER.md` | 引用 `source:<id>` |
| 顺序与里程碑完成 | `ROADMAP.md` | `TODO.md` 只登记单点，不定义顺序 |
| 某工作项当前状态 | `TODO.md` | `ROADMAP.md` 只给里程碑汇总，不镜像逐条状态 |
| 某文件现在什么状态 | `STATE.md` + git 跟踪事实 | 其他文件不重复声明 |
| 已发生什么变更 | `CHANGELOG.md` | 只追加，不改写 |
| 发现过什么错误 | `ERRATA.md` | 可关联 `T-xxx`，不定义计划 |

**裁决顺序**：

1. 事实冲突（文件是否存在、是否可用）：以 `git ls-files` 与 `STATE.md` 为准；两者不一致时先修 `STATE.md`。
2. 工作项状态冲突：以 `TODO.md` 为准；`ROADMAP.md` 的汇总与它不一致时修 `ROADMAP.md`。
3. 计划顺序冲突：以 `ROADMAP.md` 为准。
4. 历史冲突：以 `CHANGELOG.md` 已登记批次为准；发现错误时追加更正，不回改。
5. 语义冲突：按 2.1 的上位层裁决。

### 2.4 新增、合并、废弃

- **新增**：`ROADMAP.md`，根目录，调度层。职责是目标、里程碑、出口条件、关键路径、发布点。
- **不合并**：`STATE.md` 与 `CHANGELOG.md` 保持分离（现状 vs 历史）；`TODO.md` 与 `ROADMAP.md` 保持分离（单点 vs 顺序）。
- **不废弃**：现有调度文件全部保留。`TODO.md` 的“唯一登记处”表述收窄为“单点工作项状态的唯一登记处”。
- **不拆目录**：不把 `TODO.md` 拆成按里程碑的多文件，避免破坏 `check_anchors.py` 的行首编号解析与历史编号追溯。

## 3. 需要动的条文

以下逐条给出改法。所有涉及 `CONSTITUTION.md` 的改动按第 4 条附 ADR，并引用具体受影响对象；**保护清单不动**。

### 3.1 `CONSTITUTION.md`

**改动 A（第 4 条，最小且必需）**

在“实质性修改必须附 ADR”的清单之后加一句：

> 调度层文件（`ROADMAP.md`、`TODO.md`、`STATE.md`、`CHANGELOG.md`、`ERRATA.md`）的变更不构成本条所称实质性修改；其纪律由 `AGENTS.md` 的 schedule 条款规定，且不得改变任何规范语义。

- **意图**：给计划层一个明确的“不属于立法修改”的位置，避免每改一次里程碑都要 ADR，同时用最后半句防止借调度层改规则。
- **受影响对象**：`GRAMMAR.md` 的 G-B1、G-B2（其状态签注与 `validation/CHECKLIST.md` 不一致，是本次治理失败的实例），以及 `TODO.md` 的 T-118。
- **为什么需要**：不写这一句，`ROADMAP.md` 的任何顺序调整都可能被解释为需要 ADR，计划层无法运转。

**改动 B（第 1 条，可选，仅完整方案）**

在三权分立表之后加一句：

> `ROADMAP.md`、`TODO.md`、`STATE.md`、`CHANGELOG.md`、`ERRATA.md` 构成调度层；调度层不属于上述三权，不产生规范语义，只记录顺序、状态与历史。

- **意图**：消除“调度文件没有位置”的诊断 G1。
- **代价**：宪法增加一段非规范性说明；最小方案可不做，因为 `AGENTS.md` 已能承载。

**改动 C（第 5 条第 2 项，仅完整方案）**

把“该 ADR 必须引用至少一个 `GRAMMAR.md` 中的规则或 `SOURCE_LEDGER.md` 中的条目”扩展为“或引用本文件中具体条款与可复现的治理失败”。

- **意图**：解决纯治理结构调整无法满足“受影响对象”的程序死锁（诊断 G3）。
- **风险**：放宽了修改本文件的门槛。缓解：保留“必须说明具体治理失败”与原保护清单不变，并明确“此扩展不适用于降低保护清单强度的修改”。
- **注意**：这是对第 5 条本身的修改，仍须走第 5 条的程序；最小方案**不做**此项，改用下面的替代做法。

**最小方案下的替代做法**：本次 ADR 以 G-B1、G-B2 与 T-118 作为受影响对象，说明“规则状态签注无法在现有调度文档中排序与验收”这一具体治理失败。这样无需改第 5 条第 2 项即可完成本次落库；第 5 条第 2 项的扩容留作后续独立提案。

## 4. 迁移方案

### 4.1 落库顺序

1. 提交本提案与 `ROADMAP.md`（仅文档，不改条文）。
2. 批准后写 ADR-0011（调度层，文件待创建），状态 `accepted`；`affected_files` 列出第 3 节的全部位置。
3. 按第 3.1 节改动 A 修改 `CONSTITUTION.md`。
4. 按第 3.2 节修改 `AGENTS.md`。
5. 按第 3.5 节重组 `TODO.md`。
6. 按第 3.3、3.4 节更新 `README.md`、`README.en.md`、`STATE.md`。
7. 运行四个检查器；若规则或来源文本块未改动，锚点基线不需要重冻。若因状态签注文本变更触发漂移，按 `spec/ANCHOR_SPEC.md` 用 `--write-baseline` 重冻，并与内容变更同批提交。
8. 追加 `CHANGELOG.md` 批次（记录 ADR-0011 与全部文件），打发布点或并入 M0 的 `v0.5.0`。

### 4.2 防断链

| 断链面 | 风险 | 措施 |
|---|---|---|
| `todo:T-xxx` 引用 | 重组章节后编号丢失或行首格式变化 | 编号不变；每行保持 `| T-xxx |` 行首格式；迁移后运行 `check_anchors.py`，确认待办集合不减少 |
| 计划新条目 | 先写进 `ROADMAP.md` 却未登记 `TODO.md` | 规定顺序：先登记 TODO，再引用；未登记的条目不得只在计划里出现 |
| `check_state.py` | 新增 `ROADMAP.md` 被判漏登 | 根目录默认 `active` 已覆盖；无需改脚本 |
| `check_anchors.py` 基线 | 误以为新增文档会改变指纹 | 基线只含 `rule:` 与 `source:` 文本块；计划与提案不进入基线 |
| 章节引用 | 把 `AGENTS.md` 的 3.2 写成“第 3.2 条”，检查器判为不存在 | 统一写“`AGENTS.md` 的 3.2”，不使用“第 … 条”形态 |
| 计划中文件 | 在文档中反引号写尚未创建的 `.md` 路径 | 同一行标注“待编写”或“计划创建”，或改用文字描述 |
| `manifest.json` | 发布后只改 tag 不改 `manifest.json` | T-110 的检查项在 M0 落地，发布前强制运行 |

### 4.3 回滚

- 本提案与 `ROADMAP.md` 是独立提交，可单独回退。
- ADR-0011 在 `accepted` 前保持 `proposed`；条文改动与 ADR 同批提交，回退时一并回退。
- `TODO.md` 的重组不删除任何行；回退只恢复章节标题与新增列，不影响工作项内容。

## 5. 代价与风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 新增漂移面 | `ROADMAP.md` 与 `TODO.md` 可能对同一件事给出不同状态 | 粒度规则：计划只写里程碑级，台账只写单点级；里程碑汇总不复制单点状态；冲突按 2.3 裁决 |
| 宪法膨胀 | 在 `CONSTITUTION.md` 增加调度层说明会让它承担描述职责 | 最小方案只加第 4 条一句；调度层细节留在 `AGENTS.md` |
| 程序放宽 | 第 5 条第 2 项扩容会降低修改宪法的形式门槛 | 最小方案不改；如做完整方案，保留“必须说明具体治理失败”，并明确不适用于保护清单 |
| 检查器改动 | 新增计划一致性检查会引入新脚本与新失败模式 | 最小方案不新增脚本；T-110 的 manifest/tag 检查并入既有脚本框架 |
| 计划僵化 | 里程碑写得过细会变成第二套 TODO | 出口条件只写可验证结果，不写步骤；步骤留在 TODO |
| 权威二次冲突 | `AGENTS.md` 已声明目录结构权威，新增 3.4 后可能与 3.2 竞争 | 3.2 明确“状态权威”，3.4 明确“顺序权威”，两者不重叠 |

## 6. 两档方案

| 维度 | 最小方案 | 完整方案 |
|---|---|---|
| `CONSTITUTION.md` | 只加第 4 条一句（改动 A） | 改动 A + 第 1 条调度层说明 + 第 5 条第 2 项扩容 |
| `AGENTS.md` | 3.1/3.2 修补 + 新增 3.4 + 目录树与责任表 + 第 8 条两条 | 同左，另加 3.3 的审批流细化 |
| `README.md` / `README.en.md` | 文件地图一行 + 发布段改为指针 | 同左，另加调度层阅读路径小节 |
| `STATE.md` | 维护规则加一句 | 增加“产物基线”字段（`source_commit`）与对应说明 |
| `TODO.md` | 按里程碑重组、加列、统一状态、补 `blocked-external` | 同左，另把重复项真正合并为一条并保留交叉编号 |
| 检查器 | 不新增；T-110 的 manifest/tag 检查并入现有脚本 | 新增调度一致性脚本，核对 TODO 里程碑集合与 ROADMAP 一致、manifest 与 tag 一致 |
| ADR | ADR-0011 一份 | ADR-0011（调度层）+ ADR-0012（发布治理） |
| 风险 | 低；计划与台账的粒度靠文字纪律约束 | 中；多一个脚本与一条检查链，但漂移可被机械发现 |

**推荐：最小方案，加一个增量**——把 T-110 的 `manifest.json` 与 tag 一致性检查并进现有脚本。理由：

1. 当前最真实的漂移是发布点（11 个提交无 tag、`manifest.json` 停在 0.4.0），而它不是靠新的计划文档能解决的，必须有检查。
2. 治理结构的其余部分（调度层、四文档分工）用文字纪律足以约束，暂不值得为它增加第二个检查脚本。
3. 第 5 条第 2 项的扩容涉及降低修宪门槛，应作为独立提案单独立论，不夹带在本次改造里。
