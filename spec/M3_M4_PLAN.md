## 1. 范围与出口：现有条件够不够当验收依据

### 1.1 M3（本体定义）

**要产出什么**：T-126 为 124 个工件与 185 个工具与技术补齐自写定义（当前 `taxonomy-only`）；写不出者保持 `pending` 并写原因。T-132 评估并撤除缺口台账临时机制（或按规则冻结）。

| 现有出口 | 可否验收 | 缺口 |
|---|---|---|
| 1. 给出完成数量 + 显式 `pending` 清单，原因不得是原文改写 | 只能验收“有没有”，不能验收“定义是否可用” | 无质量判据；无抽样外核；`pending` 原因无法机器判定是否合格 |
| 2. `validate_ontology.py --matrix` 通过，24 条形状仍判出 | 可验收结构，不足以验收定义 | 形状只约束结构，`taxonomy-only` 也能通过 |
| 3. 形状 ↔ 规则文本 P1c 对照由 T-125 完成并落 ADR | 可验收，但该出口属于 M4 | M3 自己无法独立关闭出口 3 |
| 4. 换版维护程序写入 `ontology/README.md` | 可验收“有没有”，不验收程序可执行性 | 未要求演练一次换版或给出重跑命令清单 |
| 5. 无到期未裁定缺口；T-132 撤除或冻结 | 当前不可达 | 缺口台账仍有 5 条 `open`；撤除要求连续两个发布点 `open=0` + 核查矩阵 17/17，与 M2 受阻于外部基础设施直接冲突 |

**结论**：现有出口**不够**。出口 1 只计数量、出口 2 只验结构、出口 3 跨到 M4、出口 5 在当前治理状态下不可达。T-132 的“撤除”判据应改为“显式冻结 + ADR 说明”，否则 M3 会被一个不可达条件永久卡住。

**可判定的替代判据（建议）**：

- M3-E1：309 条逐条有 `definition` 字段；`definition` 非空、非 `taxonomy-only`、非 `pending` 的条数 ≥ 试点放量后约定阈值；每条 `pending` 必须含 `pending_reason ∈ {source_insufficient, concept_ambiguous, needs_external_review}` 与解锁条件。
- M3-E2：外部抽样核对 N 条（建议 N=30，覆盖 5 个工件类别 + 5 个工具类别）；抽样由**非执行方**持来源页码逐条核对，结论落外部产物（路径 + sha256），不以本仓库自测代替。
- M3-E3：术语一致性：同一概念在 `GLOSSARY.md`、`anchored-entries.jsonl`、本体 `skos:prefLabel` 三处的名称/ID 映射零冲突（机器可查）。
- M3-E4：换版程序必须能在**不修改代码**的前提下按 `ontology/README.md` 重跑一次 `--matrix` 并产出同一结论。
- M3-E5：T-132 改为二选一并落 ADR：撤除（仅在 `open=0` 且外部复核判实质收敛时）或**冻结**（写明冻结条件、复审触发点、不得新增依赖）。

### 1.2 M4（来源收口）

**要产出什么**：17 项工作，核心是让每个来源条目有 `status`、`verification_method`、`allowed_uses`、`compilation_landing`，外部不可得时有规则可依；落 2–3 条 ADR。

| 现有出口 | 可否验收 | 缺口 |
|---|---|---|
| 1. 每个 active 条目四字段齐全且落点真实存在 | 可机器验收 | 只验字段与落点存在，不验 `allowed_uses` 是否被遵守、`claim_mapping` 是否真实支持该论断 |
| 2. 无悬空 `pending:T-xxx`；不可得条目按 T-106 标记 | 可验收，前提是 T-106 先定 | T-106 本身是 open；规则未定前该项无法判定 |
| 3. G-B1/G-B2、G-F1–F4、G-G1–G3 锚定结论落 ADR，`GRAMMAR.md` 状态注一致 | 可验收一致性，不验收结论正确性 | 结论正确性依赖外部原文；无抽样外核 |
| 4. T-123、T-125 落 ADR | 可验收“有没有 ADR” | 不验收 ADR 结论是否有事实依据 |
| 5. T-121 人工发送结果如实记录 | **不可机器验收** | 只能靠外部证据（邮件 message-id、发送截图、复核方确认）；“如实”本身不可机械判定 |

**结论**：现有出口**部分够用**：字段与落点、状态注一致性可机器验收；事实正确性与“如实记录”不可。需要把“外部事实”从“本仓库自测”中拆出来。

**可判定的替代判据（建议）**：

- M4-E1：`SOURCE_LEDGER.md` 每个 active 条目四字段齐全，落点经 `check_ledger_landings.py` 验证存在（机器）。
- M4-E2：`claim_mapping` 抽样核对：每个来源抽 2 条论断，核对“原文位置 → 规则/条目文本”的对应关系；抽样结论落**外部产物**（路径 + sha256），由非执行方核对。
- M4-E3：T-106 先落 ADR，给出 `blocked-external` 的三种处置（长期不可得 / 部分可得 / 取得后重评）与状态迁移；在此之前 M4-E2 只对 `verification_method != pending` 的条目生效。
- M4-E4：`GRAMMAR.md` 状态注与 ADR 结论逐条一致（机器可查：`assumption` / `pending_reanchor` / `active` 三值）。
- M4-E5：T-121 以“外部证据指针”验收：邮件 message-id 或发送截图的外部路径 + sha256，由复核方下一轮核对；**不得**以仓库内文字声明记为已发送。

## 3. 试点方案

**目标**：在放量前用最小批量验证 R1–R10 中“现在必须定”的六项，尤其是 R1/R2/R3/R5/R6。

**批量（建议 15 条 + 1 契约 + 1 产物）**：

- 6 个工件定义：`ProjectCharter`、`BusinessCase`、`BenefitsManagementPlan`、`IssueLog`、`RiskRegister`、`QualityReport`（覆盖 document / register / plan 三类）。
- 6 个工具与技术定义：`AlternativesAnalysis`、`CostBenefitAnalysis`、`DecisionTree`、`MonteCarloSimulation`、`EarnedValueAnalysis`、`RootCauseAnalysis`（覆盖 data gathering / analysis / modeling 三类）。
- 3 条过程或绩效域定义：从 `pmbok8-processes.ttl` 选 1 个过程、1 个焦点区、1 个绩效域，验证“过程类条目”与“工件/工具类条目”是否共用同一字段结构。
- 1 个领域契约：复用 `contracts/examples/` 的槽位结构，新增 1 份试点契约（不引入领域词进 `GRAMMAR.md`）。
- 1 份编译产物：从 `validation/CHECKLIST.md` 摘出试点相关行，按 R5 的候选格式生成一份样例产物，供 3 类消费者读取。

**试点验收判据**：

1. 15 条全部有 `definition`、`grounding_ref`、`sourcePage`、`definitionStatus`，且无 `taxonomy-only`。
2. 每条定义的来源回溯可在 1 次检索内完成（从条目到来源页码，不靠人工记忆）。
3. 规则 ↔ 条目双向解析：G-A1/G-A2/G-C1/G-D1/G-E1 每条至少 1 个条目可双向解析，零歧义。
4. 同一概念四处命名零冲突（GLOSSARY / JSONL / TTL / 规则引用）。
5. 1 份产物可被 3 类消费者读取，无需改格式。
6. 3 组冲突样例都能在现有字段内记录，且不丢“谁与谁冲突”。
7. 外部抽样：由非执行方抽 5 条，按来源页码核对定义是否“自写且不失真”，结论落外部产物（路径 + sha256）。

**止损条件（出现任一条即停止放量，先改结构）**：

- 试点的 15 条中 ≥2 条无法在现有字段内表达（需要加字段或改粒度）。
- 规则 ↔ 条目双向解析出现 ≥1 条歧义或需要引入新规则。
- 3 类消费者中有任意 1 类要求改产物格式。
- 冲突样例有任意 1 组无法记录双方立场。
- 外部抽样 5 条中 ≥2 条被判“改写原文”或“定义不可用”。
- 为通过试点需要新增检查器、指纹区段或自证机制。

## 4. 串并行安排

**必须串行**（同仓库文件冲突或依赖未定）：

1. R1 条目字段与粒度 → 试点草稿 → R2 绑定方式 → R3 ID 形态。三者同一批文件，不能并行改。
2. R6 冲突记录格式 → 试点 3 组冲突样例 → 放量。冲突格式未定时不写 `claim_mapping`。
3. R5 产物格式 → 试点产物 → M5/M6 消费者。消费者未定时不批量生成产物。
4. M4 T-106 处置规则 → M4 出口 2/3 的判定；T-106 未定时 `blocked-external` 条目只能保持原状。
5. M4 T-123 → T-125（P1c 对照依赖 T-123 的来源用途结论）。

**可以并行**：

- M3 的 6 个工件与 6 个工具可分成两组并行写草稿（不同文件、不同类别）。
- M4 的本地可核验项（T-004、T-005、T-006、T-007、T-094）可与 M3 试点并行；它们不改本体结构。
- M4 的 `blocked-external` 项（T-052、T-112、T-115、T-119、T-121）可并行等待外部输入，但不得在等待期间改来源表结构。
- 外部抽样（M3-E2 / M4-E2）可与条目写作并行，但抽样结论必须晚于对应条目定稿。

**依赖顺序（列表）**：

```
R1 → 试点草稿 → R2 → R3
R6 → 冲突样例 → 放量写 claim_mapping
R5 → 试点产物 → M5/M6 消费

M4 本地核验（T-004/005/006/007/094） → M4 外部核验（T-001/002/003/052/112/115/119/121） → M4 出口
```

## 6. 明确不做什么

1. 不新增检查器、不新增指纹区段、不新增钩子步骤。现有 10 个检查器与 7 个指纹区段保持不变。
2. 不重启自证类机制：不以“本仓库脚本全绿”“原型 60/60”“哈希一致”作为 M3/M4 的内容验收。
3. 不以同源产物充当外部证据；复核记录不得由执行方转录为依据。
4. 不写“逐句改写原文”的定义；写不出就 `pending`，不凑数。
5. 不在试点前批量写 309 条，不在结构未定时生成编译产物。
6. 不借 M3/M4 扩 `GRAMMAR.md` 的规则组或 `CHECKER_INPUT_SCHEMA.md` 的字段。
7. 内容验收以外部可核对事实为主：来源页码、条款、可复现检查；单条定义是否“自写且不失真”由非执行方抽样核对。
