# 自建 PMBOK 本体的可行性评估与方案对比

**性质**：评估报告，非规范。结论不改变任何规则、来源或检查项；是否落地由 `TODO.md` 的工作项与后续 ADR 决定。
**评估对象**：从本地 `resources/pm/` 的 PMBOK 8th（2026，401 页）自建一个小规模、以约束为主的本体，用作概念层来源、可判定约束来源、负例生成 oracle、跨标准映射锚。
**基线方案**：手工知识条目（10 条）+ 反例用例（3 个）+ 全文档级编译（`validation/CHECKLIST.md`，17 个 `check_id`）。

**标注约定**：`[已核实]` 指本次从本地正文或仓库文件直接读到；`[推断]` 指基于结构作出的判断；`[不确定]` 指现有材料不足以判断。

---

## 0. 结论

1. **建议做，但只做一层**：做“概念骨架 + 8–12 条 SHACL 形状 + 3 个 fixture”的最小原型，状态记为 `skeleton`、非规范；**不做** 40 流程 × 100+ 产物的全量本体，**不**把本体提升为 `grounding_ref`，**不**新增独立编译方法。
2. **技术上可行，治理上先卡住**：技术侧的主要约束是“写定义不能逐句对应原文”，不是工具；治理侧的真正阻塞是 `PMBOK8-2025` 的 `allowed_uses` 目前只允许“原则层交叉验证”，不允许作为概念层或规则锚定依据。后者需单独 ADR，不在本次评估与治理放宽范围内。
3. **用户原推断需要更正**：`[已核实]` PMBOK 8th **恢复**了过程式结构——5 个 Focus Areas（由 Process Groups 重述而来）、7 个绩效域、40 个非规定性过程，且第 4 章给出输入/输出、第 5 章给出工具与技术。因此“第 8 版缺少过程式类层次”不成立；它缺少的是**机器可读的本体**，不是过程层次本身。
4. **收益不在“省人工”**：本体不会减少定义写作量，它增加的是机器可校验的结构与可复用的测试夹具；代价是新增一条维护链和一个新的失效源。

## 2. 目标形态与规模

### 2.1 选型：SHACL 为主，OWL-lite 为辅，不引入 DL reasoner

`[推断]` 建议采用 **SHACL Core + 少量 SHACL-SPARQL**，词汇层只用 `rdfs:subClassOf`、`owl:disjointWith` 这类轻量公理，不启用 OWL DL reasoner。理由：

1. **语义方向匹配**：现有 17 个 `check_id` 要回答的是“这份契约实例是否缺节点/缺边/取值越界”，这是闭世界校验；SHACL 的 `sh:minCount`/`sh:class`/`sh:in`/`sh:targetClass` 直接对应，OWL 的开世界语义反而无法表达“必须存在”。
2. **失败可解释**：SHACL 校验报告逐条给出焦点节点、路径与约束组件，能直接映射到 `check_id` 与 `pass`/`fail`；DL reasoner 通常只给“不一致”，难以定位到具体规则。
3. **工具与确定性**：`pyshacl` 是单进程、确定性输出；DL reasoner 的推理规模与顺序不易约束，和 `CM-DET-CHECKER` 的确定性要求冲突。
4. **需要 OWL 的地方有限**：类层次与互斥（如 `Project` 与 `Portfolio`）用 `rdfs:subClassOf`/`owl:disjointWith` 足够；需要“两个断言不得同时成立”的规则（如 `ASSERTION_MUTUAL_EXCLUSION`）SHACL Core 表达不了，须用 SHACL-SPARQL，或继续由现有检查器承担。

`[推断]` 因此“SHACL 形状约束而非全 OWL DL + reasoner”的方向正确；但要接受一个后果：**部分规则只能做到 `advisory` 或 `cannot_evaluate`**，不能宣称本体让全部规则变成可判定。

### 2.2 规模估计（v0 原型 / 全量）

| 项目 | v0 原型 | 全量（不建议现在做） |
|---|---|---|
| 类 / 受控词表 | 55–65（7 域 + 5 焦点区 + 40 过程 + 约 10 个核心概念） | 80–100（再加产物类别、角色、约束类型） |
| 对象属性 | 12–18 | 25–35 |
| 个体 | 40 个过程 + 20–30 个核心产物 | 40 过程 + 100–150 产物 + 约 200 工具与技术 |
| SHACL 形状 | 8–12 | 20–30 |
| 文件 | 3 个 `.ttl` + 3 个 fixture + 1 个脚本 | 8–12 个 `.ttl` |
| 行数 / 体积 | 约 1.5k–3k 行，< 200 KB | 约 4k–6k 行，< 400 KB |

`[已核实]` 当前检查器单文件上限 512 KiB，全量本体仍在限内；但体积不是主要成本，定义写作与复核才是。

### 2.3 术语与定义的边界

| 可以直接取自标准 | 必须自述转述 | 禁止 |
|---|---|---|
| 标准术语名（如 40 个过程名、7 个域名的**名称**） | 每个类/属性的定义（一句话，自己的措辞） | 逐句对应原文的改写、同义词替换式洗稿 |
| 层级与归属事实（某过程属于某域/某焦点区） | 对关系的说明（为何这条边存在） | 原文段落、项目符号列表、表格行、图注的转录 |
| 印刷页/章节定位 | 术语的适用范围与本技能中的用法差异 | 整页转储、OCR 全文、目录点线、页码序列 |
| `skos:prefLabel` 用术语名 | `skos:definition` 用自写句 | 以“可替代原作”为目标的实质内容复刻 |

`[推断]` 操作规则：**写不出自述定义时，只保留术语名 + 页码，把 `definition_status` 标为 `pending`**，不要用原文改写凑数。这条规则同时是检查器 `RM-ONTO-LITERAL` 的语义基础。

## 3. 最小可跑原型

### 3.1 构成

| 文件 | 内容 | 验收 |
|---|---|---|
| `ontology/pmbok8-core.ttl` | 命名空间、7 域、5 焦点区、40 过程、约 10 个核心概念；术语名 + 页码 + 自写一句话定义 | `rdflib` 可解析；每个术语有 `dcterms:source` 与 `pm:sourcePage` |
| `ontology/pmbok8-shapes.ttl` | 8–12 条形状，`pm:implementsCheck` 指向**已有** `check_id` | 不新增 `check_id`；每条形状能对应到 `validation/CHECKLIST.md` 的一行 |
| `ontology/fixtures/valid.ttl` | 最小合规图 | `pyshacl` 报告 `conforms: true` |
| `ontology/fixtures/invalid-*.ttl` | 2–3 个定向违规图 | 每个只触发预期的那条形状，报告可定位 |
| 包装脚本（`scripts/` 下，待建） | `pyshacl` 包装：输入数据图 + 形状图，输出 `check_id` 级结论与退出码 | 0 通过 / 1 违规 / 2 结构或依赖错误 |

建议的 10 条形状（全部对应已有检查项）：`PROJECT_MINIMAL_EXISTENCE`、`CONSTRAINT_ANCHOR_REQUIRED`、`DELIVERABLE_ASSERTION_REQUIRED`、`ASSERTION_SUBJECT_REQUIRED`、`COMMITMENT_LINK_REQUIRED`、`ACCOUNTABLE_UNIQUE`、`RESPONSIBLE_DECLARED`、`DELEGATION_DECLARED`、`DUAL_DIMENSION_ANNOTATION`、过程/域归属完整性。

### 3.2 工具链

`[已核实]` 当前 Python 环境**没有** `rdflib` 与 `pyshacl`（导入均失败）；需要 `pip install rdflib pyshacl`，可选 `owlrl`。这意味着：

- 原型不是“零依赖”的；它给仓库增加一条 Python 依赖链与版本钉扎需求。
- 若宿主无法安装依赖，本体只能作为**文档级参考**，不能作为可执行检查；这与 `CM-DET-CHECKER` 的“无插件完备性”不冲突，但要让本体保持**可选**。

### 3.3 工作量（按构成计，不给时间估计）

- 建模：40 个过程与 7 个域的骨架是机械工作；难点在 10 个核心概念与 10 条形状的边界对齐。
- 定义：约 60–80 条自写定义，是**不可压缩**的人工成本；这也是本体相对手工知识条目**没有明显节省**的部分。
- 校验：3 个 fixture 与 1 个包装脚本，工作量小。
- 复杂度集中点：不是工具链，而是“形状是否真的等价于规则文本”的论证（P1c“不扭曲”）。

## 4. 与现有结构的接合

| 现有结构 | 接合方式 | 风险 / 约束 |
|---|---|---|
| `GRAMMAR.md` | 不改规则文本；形状用 `pm:implementsRule` 与 `pm:implementsCheck` 反向标注 | 本体是**派生工件**，不是来源；`grounding_ref` 仍须指向 `SOURCE_LEDGER` 的 active 条目 |
| `knowledge/anchored-entries.jsonl` | JSONL 继续是 A 类概念的权威；本体通过 `pm:anchoredEntry` 指针引用，不复制定义 | 两处同时写定义会产生“双真相源”；v0 只做单向引用 |
| `validation/CHECKLIST.md` | 每条形状对应一行已有检查项；CHECKLIST 仍是人类可读的权威投影 | 当前 B 组检查项的状态注记过期（仍写 `pending_reanchor`），映射前须先重建 |
| `CM-DET-CHECKER` | `pyshacl` 作为宿主“其他谓词求值能力”的一种实现；不新增方法 | 若形状成为**编译产物本身**，则属于方法层变更，需按 META 第 3 条另行论证；v0 不这样做 |
| `SOURCE_LEDGER.md` | `PMBOK8-2025` 目前只允许“原则层交叉验证” | **这是当前真正的阻塞**：作为概念层来源需先修订 `allowed_uses` 与 `claim_mapping`（ADR） |

`[推断]` 最稳妥的接合是“**本体非规范、CHECKLIST 权威、pyshacl 只是执行器之一**”。这样即使本体写错，也不会改变任何规则的编译结论；代价是本体的收益被限制在“辅助校验与查询”，不能直接充当规则依据。

## 5. 四项用途的可实现程度

| 用途 | 程度 | 依据 |
|---|---|---|
| 概念层来源 | **高（技术）/ 当前受阻（治理）** | 术语与层级事实足以支撑 A 类概念的结构化；但 `PMBOK8-2025` 的 `allowed_uses` 不允许作概念层依据，需先改来源表 |
| 可判定约束来源 | **高（结构性约束）/ 低（时序与跨产物语义）** | 存在性、基数、取值域、边指向可直接用 SHACL；过程顺序、时间窗、跨产物比对超出 SHACL Core，仍需现有检查器或人工 |
| 负例生成 oracle | **中** | 形状可判定“哪条违规”，据此可为每条形状生成一个最小违规图；但“最小化”与复杂形状（互斥、跨节点）仍需手工 fixture，不能全自动 |
| 跨标准映射锚 | **低–中** | 可在图中存 `skos:closeMatch`（PMBOK 过程 ↔ ISO 21502 实践 ↔ PRINCE2 过程），带来源与置信度；但等价性是解释判断，本体不能验证，只能承载 |

## 6. 与当前方案的逐项对比

| 维度 | 当前方案 | 自建本体（v0） |
|---|---|---|
| 概念条目 | 10 条 JSONL，人工撰写、已复核 | 55–65 个类/词表项；定义仍需人工撰写，**不省定义工作量** |
| 可执行性 | 17 个 `check_id` 只有文档级清单，无可执行原型（T-107） | 8–12 条形状可执行；覆盖的是结构性子集，不是全部 17 条 |
| 反例 | 3 个手写用例 | 形状 + 3 个 fixture；可再自动派生少量违规图 |
| 跨标准映射 | 无结构化载体 | 可承载映射图，但映射本身仍需人工论证 |
| 一次性成本 | 0 | 约 7 个文件、1.5k–3k 行、1 条 Python 依赖链、1 个包装脚本 |
| 持续维护 | 规则变更时改 JSONL/CHECKLIST | 规则变更 + PMBOK 换版 + 依赖升级 + 形状与规则文本对齐，**维护面明显变大** |
| 新增失效源 | 少 | 本体写错、形状空转（vacuously true）、图与规则漂移、依赖不可用、版权风险 |
| 治理冲击 | 无 | 新增“派生工件”类别；来源 `allowed_uses` 需 ADR；检查器需扩展（本次已做）；可能引出方法层 ADR |
| 可验证性 | 人工评审 | 本体与 fixture 可机器校验；但“形状是否忠实于规则”仍需人工论证（P1c） |

**净判断** `[推断]`：收益是“结构化 + 可执行的结构检查 + 可复用 fixture + 映射载体”；代价是“不省定义、维护面变大、新增失效源、治理变更”。在只有 17 条规则、10 条知识条目的规模下，**全量本体不划算**；**最小骨架划算**，因为它同时为 T-107（可执行原型）和 T-101（反例补齐）提供了低成本路径。

## 7. 建议

**做**：

1. 只做 v0：概念骨架 + 10 条形状 + 3 个 fixture + 1 个包装脚本，状态 `skeleton`，不进入 `grounding_ref`。
2. 先做一次“形状 ↔ 规则文本”的逐条对照，证明不扭曲（P1c）；不能证明的规则，形状不覆盖，显式列为不可映射项。
3. 把 `pyshacl` 定位为宿主执行器之一；`validation/CHECKLIST.md` 仍是权威投影。

**不做**：

1. 不做 40 过程 × 100+ 产物的全量本体。
2. 不把本体写成新的来源，不改 `grounding_ref`。
3. 不启用新的编译方法，不把 SHACL 形状当作编译产物本身。
4. 不在未解决许可问题前公开发布本体。

## 8. 不确定项

1. **版权/许可** `[不确定]`：本地副本声明仅限个人使用、禁止 AI 训练、禁止复制。自建本体若复刻了 40 个过程的集合与 I/O 编排，是否构成衍生作品，属于法律判断，现有材料不足以定论；公开仓库（MIT）发布前应做一次许可审查。这是本评估中**最大的未量化风险**。
2. **形状表达力** `[不确定]`：`ASSERTION_MUTUAL_EXCLUSION` 等规则能否用 SHACL-SPARQL 忠实表达，需在原型中验证；在验证前不应声称“可判定”。
3. **宿主可执行性** `[不确定]`：部署环境是否允许安装 `pyshacl`、是否接受新增依赖，未知；因此本体必须保持可选。
4. **PMBOK 换版** `[推断]`：第 8 版刚引入 40 过程结构，后续版本可能再次调整；本体的长期维护成本可能高于一次性成本。
5. **规模数字** `[推断]`：§2.2 的数量级来自结构计数与建模经验，未经原型实测；以原型产出为准。
